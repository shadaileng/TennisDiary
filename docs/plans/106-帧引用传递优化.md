# 106：帧引用传递优化

## 一、背景与目标

### 1.1 问题描述

当前电子教练分析流程中，frames（base64 图片数据）在前后端之间传输了 3 次：
1. `POST /api/video/upload` → 返回 frames 给前端
2. `POST /api/ai/analyze` → 前端发送 frames 给后端
3. `POST /api/pose/analyze` → 前端发送 frames 给后端

每帧 base64 约 200KB，7 帧约 1.4MB，3 次传输约 **4.2MB**。

### 1.2 目标

改为引用传递：前端只传文件路径（frame_urls），后端根据路径读取文件。

**传输量对比**：

| 方案 | 总传输 |
|------|--------|
| 当前 | ≈ 4.2MB |
| 引用 | ≈ 600B |

**节省约 99.98%** 的前后端帧数据传输量。

## 二、现状分析

### 2.1 帧文件已存在

`POST /api/video/upload` 已将帧保存为文件：
```
data/uploads/videos/{user_id}/{uuid}_f0.jpg
data/uploads/videos/{user_id}/{uuid}_f1.jpg
...
```

并返回 `frame_urls: string[]`（相对路径数组）。

### 2.2 下游服务需求

| 服务 | 需求格式 | 当前来源 |
|------|---------|---------|
| AI 分析 | `data:image/jpeg;base64,...` | 前端传入 frames |
| 姿态分析 | JPEG bytes | 前端传入 frames |

### 3.3 后端：AI 服务修改

**文件**：`server/app/services/ai_service.py`

新增帧读取辅助函数：

```python
def _load_frames_from_urls(frame_urls: list[str]) -> list[str]:
    """从文件路径读取帧，返回 base64 dataURL 列表"""
    import base64
    import os
    from app.core.config import settings

    frames = []
    for url in frame_urls:
        path = os.path.join(settings.UPLOAD_DIR, url)
        if os.path.isfile(path):
            with open(path, "rb") as f:
                data = base64.b64encode(f.read()).decode()
            frames.append(f"data:image/jpeg;base64,{data}")
    return frames
```

### 3.5 前端：API 封装修改

**文件**：`miniapp/src/services/data.ts`

```typescript
export function analyzeSwing(
  frameUrls: string[],  // 改为接收 frame_urls
  kind: string,
  mode: "single" | "full",
): Promise<AnalysisReport> {
  return post<AnalysisReport>(
    "/ai/analyze",
    { frame_urls: frameUrls, kind, mode },
    { timeout: 120000 },
  );
}

export function analyzePose(
  frameUrls: string[],
  options?: {
    videoUrl?: string
    saveSkeleton?: boolean
    duration?: number
    frameRate?: number
    fullFrames?: boolean
  },
): Promise<PoseResult> {
  return post<PoseResult>(
    "/pose/analyze",
    {
      frame_urls: frameUrls,
      video_url: options?.videoUrl,
      save_skeleton: options?.saveSkeleton ?? false,
      duration: options?.duration,
      frame_rate: options?.frameRate,
      full_frames: options?.fullFrames,
    },
    { timeout: 60000 },
  );
}
```

## 四、数据流对比

### 4.1 当前流程

```
前端 → upload → 后端返回 frames (base64 ~1.4MB)
前端 → ai/analyze { frames } → 后端接收 frames (~1.4MB)
前端 → pose/analyze { frames } → 后端接收 frames (~1.4MB)
```

### 4.2 优化后流程

```
前端 → upload → 后端返回 frame_urls (~200B)
前端 → ai/analyze { frame_urls } → 后端读文件 (~200B)
前端 → pose/analyze { frame_urls } → 后端读文件 (~200B)
```

## 五、兼容性

- `frames` 字段保留为可选，兼容旧版前端
- 新版前端传 `frame_urls`，后端优先使用
- 后端读取失败时回退到 `frames`（如有）
