# 后台三件套改造评估（HF Space + Supabase + KODO）

> ⚠️ **五项方案决策已由人类确认（见「七、决策记录」），但尚未实施任何代码。** 实施按「六、分阶段实施计划」串行推进，每阶段开工前需人类确认（七牛凭据 / Supabase 项目 / HF Space 就绪）。

## 一、评估背景与目标

拟将后台从当前「魔搭创空间 Docker + SQLite + 本地磁盘」迁移为：

| 组件 | 目标选型 | 替换现状 |
|------|---------|---------|
| 计算/部署 | Hugging Face Space（Docker Runner + FastAPI） | 魔搭创空间（当前启用，CI 就绪） |
| 数据库 | Supabase PostgreSQL | SQLite × 3（主库 / audit.db / backup_meta.db） |
| 文件存储 | 七牛云 Kodo（S3 兼容对象存储） | 容器本地磁盘 `UPLOAD_DIR` |

评估维度：技术可行性、改造成本、外部依赖风险、与现有体系（测试/备份/CI/微信小程序域名）的冲突。

## 二、现状关键事实（评估依据）

| 维度 | 现状 |
|------|------|
| 数据库连接 | `app/core/database.py` 同步 `create_engine` + `SessionLocal`（**全仓无 AsyncSession**）；另有 `audit_db.py`、`backup_meta.py` 两套独立 engine |
| SQLite 特有依赖 | `app/models/file.py:43` 与迁移 `b7d41e0c9a35` 用 `sqlite_where=` 部分唯一索引；5 处迁移 `server_default=sa.text('(CURRENT_TIMESTAMP)')`；6 处 `batch_alter_table`；JSON 均为 `Text` 存字符串（`JSONList` 也是 `impl=Text`，**不依赖 SQLite JSON1 扩展**） |

| 直接读 `UPLOAD_DIR` 绝对路径的点 | `app/services/ai_service.py:32`、`app/routers/pose.py`、`app/routers/admin/system.py`（路径穿越校验）、`app/core/dirs.py` 等，需逐个排查 |

## 三、三件套逐项评估

### 3.1 HF Space Docker（FastAPI）—— 启用成本低，但收益不明确

**利好**

- 方案 63 + Dockerfile + `.env.hf.example` + `deploy-hf.sh` 全部现成，切换约 1~2 人日。
- 免费 CPU 额度、HF Secrets 管理密钥、可挂持久盘存放 `POSE_MODEL_PATH` 与临时帧目录。

**风险**

| 级别 | 风险 | 说明 |
|:----:|------|------|
| 高 | 免费 Space 必须**公开** | 私有 Space 需 PRO/HUB 订阅；需先审计仓内无硬编码密钥（密钥须走 HF Secrets） |
| 高 | `*.hf.space` **无法备案** | 微信小程序 request/uploadFile 合法域名必须已备案 → 需自备备案域名反代（与方案 63 §5.4、方案 65 §「`.ms.show` 无法备案」同一问题） |
| 高 | 跨境链路无 SLA | 大陆 → hf.space 时延与可用性弱于境内魔搭，可复用方案 67 的 Cloudflare Workers 反代模式缓解 |
| 中 | CPU 更弱 | 56s 视频管线在免费 CPU Basic 上可能翻倍；HF 对闲置 Space 存在限流/暂停机制 |
| 中 | 收益不明确 | 魔搭方案已启用且 CI 就绪（`deploy-server-modelscope.yml`），切换净收益 ≈「换一份境外免费额度」，代价是链路变差 |

**结论**：单独不值得切。仅在「魔搭不可用 / 需摆脱国内平台」时作为兜底选项。

### 3.2 Supabase PostgreSQL —— 中高成本，收益集中在备份与并发

**收益**：自动备份 / PITR、Web 控制台、可开 `uvicorn --workers N` 摆脱 SQLite 单进程写限制、500MB 对 6.9MB 绰绰有余。

**改造清单**

| # | 项 | 难度 | 说明 |
|:-:|----|:----:|------|
| 1 | 三引擎合流 | 低 | 主库 + audit + backup_meta → PG 单库多 schema（或保留 3 DSN）；补 `pool_size`/`max_overflow` |
| 2 | **Alembic 21 版本不可在 PG 直接重放** | **高** | `sqlite_where`、batch 模式、SQLite 风格 default 混杂 → 须走「基线迁移 + `alembic stamp`」或从现有 schema 生成 PG 起点。**本方案最大坑** |
| 3 | 部分唯一索引方言 | 中 | `sqlite_where` → PG 需 `postgresql_where`；漏加则历史 `deleted_at` 行造成唯一冲突，**数据导入直接失败** |
| 4 | 连接池压力 | 中 | 同步 Session + SSE 每 1s query + 56s 后台管线；Supabase 免费版经 pgbouncer 池化、并发上限低（具体以官网为准）→ 需收敛 SSE 轮询与后台连接持有 |
| 5 | 测试体系决策 | 中 | 方案 73 的 `data_test/` SQLite 隔离 + xdist `*_gw*.db` → 要么引入 PG 测试库，要么保持 SQLite 测（方言差异测不到） |
| 6 | 数据迁移 | 低 | 15 模型 / 6.9MB，导出脚本约半天 |
| 7 | 备份体系重做 | 中 | 方案 72 的 `backup_meta.db` + 恢复流程 → 改为 `pg_dump` 流程 |

**外部风险**：免费版约 7 天不活跃自动暂停（恢复需手动，期间小程序全挂）；区域选新加坡延迟尚可但无境内节点；数据出境需同步小程序隐私协议表述。

**结论**：值得做但须排期，核心难点是迁移基线（#2/#3），不是 ORM 层。

### 3.3 KODO S3 文件存储 —— 价值最高、改造面最可控

**收益**：文件从容器卷解放（扩容、迁移不丢）、七牛境内 CDN 加速、预签名 URL 可让视频/帧大流量绕过后端带宽、HF/魔搭磁盘只留临时文件与姿态模型。

**改造面**（利好：路由全走 `file_service` 门面，物理层替换集中在 `file_store.py`）

- ✅ **易迁移**：`write_bytes` / `move_into_place` / `resolve` / `exists` / `unlink` / `md5_of` / `mime_of` → S3 put/head/get/delete（单段上传 ETag = MD5，秒传预检 `HEAD` 即可）
- ⚠️ **难点一：分片秒传协议** — `pwrite_chunk` / `write_manifest` / `chunk_data_abs` / `cleanup_expired_chunks` 是自研本地分片协议（方案 140），与 S3 multipart 语义不同 → 要么保留本地 chunk 暂存后一次 `CompleteMultipartUpload`，要么改写为 S3 multipart
- ⚠️ **难点二：混合模式** — 管线必须保留本地临时盘（ffmpeg 抽帧、mediapipe 推理、骨架视频、`POSE_MODEL_PATH`）→ 最终形态是「S3 为真相源 + 本地 tmp/cache」；`ai_service.py` 等直接读绝对路径的点须逐个排查
- ✅ **读路径（决策 4，v1.3.0 修订）** — 后端**响应层下发对象存储绝对外链**，前端（`resolveUploadUrl` / `fileUrl.ts` 的「绝对 URL 直通分支」）**零改动直连**；仅 `PENDING/FAILED` 回落相对路径走后端代理、鉴权下载（admin download）仍走后端 → 详见 [147 §六](./147-阶段一KODO对象存储细化方案.md)
- ✅ **上传路径（决策 4 不变）** — 小程序 `uploadFile` 继续打后端 `/api/upload/*`，**上传完成落库后在同一请求内写对象存储**（响应前同步完成，无外链 404 窗口）→ 七牛正式域名备案**不是上传侧阻塞项**；但**外链读取需要已备案域名**（见 §四 P0）
- ⚠️ **成本** — 每次分析产生 8 帧 + 骨架视频 + 裁剪短片，视频流量为大头（存储约 0.099 元/GB/月、外网流出约 0.29~0.5 元/GB，以七牛官网为准）；需先估月增容量
- ⚠️ **域名** — 七牛测试域名有期限，正式域名须备案；`CNAME` 回源/CDN 配置

**结论**：**优先级第一**，约 3~5 人日；方案 138 已有存量批量迁移工具先例可复用。

### 3.4 多数据源与配置化（设计增补）

> 结论：**可行**。本仓库有两个现成支点：① `file_store` 物理层集中、路由不碰路径 → 可抽 `StorageBackend` 接口 + 工厂；② 动态配置系统（Phase 78）`config_registry` 已有 `data`「数据与存储」分类，支持 `SELECT` 下拉与 `SECRET` 掩码，`config_service` 请求时实时解析（DB 覆盖 > env 默认）。
> ⚠️ 硬约束：`config_service.get_config_value()` 对未注册 key 返回空串 → **任何新配置项必须在 `CONFIG_ITEMS` 注册**，不能随手塞 env。

**「多数据源」三种语义，先选一种：**

| 语义 | 含义 | 可行性 | 成本 |
|---|---|:---:|---|
| (a) 可切换 | 任一时刻只有一个活动后端，改配置后新文件写新源 | ✅ 最简 | 阶段一已含（`STORAGE_BACKEND` 开关），约 +0.5 人日 |
| **(b) 按记录路由的多源并存（推荐）** | 历史文件留在 A 源、新文件写 B 源，**读/删/引用计数按 `files` 记录走** | ✅ | **必须给 `files` 表加存储位置字段**，约 +1~2 人日 |
| (c) 双写/多云冗余 | 同一文件同时写两个源 | ⚠️ 不建议 | 一致性/成本/清理复杂度翻倍，当前数据量用不上，**明确不做** |

> **生死点**：没有 (b) 的字段，(a) 切配置 = 旧文件集体 404。

**关键设计约束（(b) 形态）**

1. `files` 表加一列 `storage`（`local://videos/1/xxx.mp4` / `kodo://<bucket>/videos/1/xxx.mp4`，或 `backend` + `key` 两列）+ Alembic 迁移 + 存量回填默认 `local`；`rel_path` 保留为相对 key，`file_service` 门面签名几乎不变；**读/删/引用计数/管理端预览按记录路由，写按当前配置的默认后端**。
2. 分片上传会话（方案 140）在 open 时把 backend 写进 `manifest.json`，**会话全程用配置快照** —— 否则会话中途改配置会把 chunk 写进另一个源。
3. 秒传预检按记录所在源 `HEAD`；`(user_id, md5)` 唯一索引只管 DB 记录，物理位置不同不影响去重语义。
4. 进行中的操作（56s 分析管线）开工时取一次配置快照传下去，**不中途重读**（`config_service` 是请求时实时解析）。
5. 凭据走 `VALUE_TYPE_SECRET`（env 默认 + `system_configs` 覆盖，与 `WX_SECRET` / `AI_API_KEY` 同模式，Admin 页已有掩码）；`backend`/`endpoint`/`region`/`bucket` 用 `STR`/`SELECT`。

**配置项草案（`data` 分类下，均需注册）**

```
storage.backend        select   local | kodo | oss | r2    （默认 local）
storage.endpoint       str      S3 兼容 endpoint
storage.region         str
storage.bucket         str
storage.access_key     secret
storage.secret_key     secret
storage.public_base_url url     预留：将来要做直链/预签名时启用
```

多源并存时扩展为 `storage.<name>.*` 命名空间，`storage.backend` 下拉改为引用某个已配置源名 —— 与 Phase 79「`ai.provider` 下拉直选引用语义」同一模式，可直接照抄。

**测试**：用内存 dict 假 backend 跑单测，CI 不依赖真实云，与**决策 5（测试 SQLite）**完全兼容。

**结论**：阶段一按 (a) 落地开关，但**接口与 `files.storage` 字段从第一天就按 (b) 设计**（升级到多源只差一个工厂循环）；(c) 不做。

## 六、分阶段实施计划（已定稿）

> 决策依据见「七、决策记录」。总原则：**串行推进（阶段一 → 二 → 三）、每阶段独立提交、独立验收、独立回滚**，阶段间不交叉改动；任一阶段回滚后不影响其他阶段成果。

### 阶段一：KODO 对象存储（7~10 人日）

> 📋 **细化方案已拆出**：[147：阶段一 KODO 对象存储细化方案](./147-阶段一KODO对象存储细化方案.md)（流程状态机、三类文件写路径、响应层外链、**文件管理 S3 同步中心**、TDD 11 Step、14 项验收、回滚）。以下为总纲摘要。

**目标**：文件真相源迁到七牛 Kodo，读写全部经后端，前端零改动。**不动 DB、不动部署。**

**前置**：七牛账号（AK/SK + Bucket + Region）；配置走 `config_registry` 注册（§3.4 草案），默认 `storage.backend=local` 即回滚开关。

**步骤**（按 TDD：先写失败用例）

1. 🔴 RED：为 `StorageBackend` 抽象层写单测 —— **内存 dict 假 backend** + S3 backend（put / head 秒传预检 / get Range / delete / MIME 兜底 / 按记录路由），确认失败
2. 🟢 GREEN：`file_store.py` 抽出 `StorageBackend` 接口 + `local` / `s3` 两实现 + 工厂按生效配置分发；`file_service` 门面与路由层**零改动**
3. **多源就绪（§3.4 (b)）**：`files` 表加 `storage` 列（Alembic 迁移 + 存量回填 `local://...`）；读/删/引用计数/管理端预览**按记录路由**，写按当前默认后端；`config_registry` 注册 §3.4 配置项（含 `SECRET` 掩码）
4. 分片秒传（方案 140）：**保留本地 chunk 暂存 → complete 时一次性上传 S3**（`pwrite_chunk` 逻辑不动）；**open 时把 backend 写进 `manifest.json`，会话全程用配置快照**（§3.4 约束 2）
5. 管线混合模式：抽帧 / 骨架 / mediapipe 仍写本地临时目录，产物登记后上传 S3 并清理；管线开工取配置快照；排查 `ai_service.py:32` 等直接读 `UPLOAD_DIR` 绝对路径的点
6. 读路径：`/api/files`、`/api/media`、admin Range 206 保持后端代理（从 S3 流式回读、透传 Range 语义）
7. 存量迁移脚本：本地 `UPLOAD_DIR` → S3 并回写 `storage` 字段（复用方案 138 批量迁移先例），迁移后本地副本保留只读
8. ⏪ 回滚：`storage.backend=local` 即回到现状（历史文件因按记录路由，始终可读）

**验收**：`ruff check . && ruff format . && pytest -q -m fast` 全绿 + 全量 `pytest -n auto`；上传 / 秒传 / 分片续传 / 下载 Range / 删除引用计数 / Admin 文件页 / 分析管线 七链路回归；**加：切换 `storage.backend` 后历史文件仍可读、新文件写新源的多源切换用例**。

### 阶段二：Supabase PostgreSQL（4~7 人日）

**目标**：生产库迁 PG，测试继续 SQLite（决策 5）。

**前置**：Supabase 项目（区域建议新加坡）；Alembic 基线方案先在分支演练通过。

**步骤**

1. 🔴 RED：CI 增加 PG 集成 job（服务容器，仅跑关键模型/路由用例），先暴露方言差异
2. 三引擎合流：主库 + `audit_db` + `backup_meta` → PG 单库 3 schema；`Settings.DATABASE_URL` 按 `APP_ENV` 切换 —— **测试/本地 `sqlite:///...data_test/...`，生产 `postgresql+psycopg://...`**
3. Alembic：新增「PG 基线迁移」，现有 21 个 SQLite 版本 `alembic stamp` 封存（PG 不重放历史）；`sqlite_where` → `postgresql_where`（**漏改会导致数据导入唯一冲突失败**）
4. 连接池收敛：`pool_size`/`max_overflow` 调参；SSE `/{id}/stream` 降频或改短连接；管线后台 Session 用后即关
5. 数据迁移演练：SQLite 6.9MB → PG 导出脚本 + 行数/关键聚合校验
6. 备份重做：方案 72 的 `backup_meta.db` 体系 → `pg_dump` 流程
7. ⏪ 回滚：`DATABASE_URL` 切回 SQLite + 本地数据快照

**验收**：同阶段一 + 生产前演练导入一次成功；**本地与 CI 提交门禁仍 100% 走 SQLite**（AGENTS 4.3 不变）。

### 阶段三：HF Space（1~2 人日）

**目标**：摆脱魔搭（决策 1），生产切到 HF Space。

**前置**：反代在**项目外**配置（决策 2，仓库内不新增反代配置，只沉淀契约）。

**步骤**

1. 复活方案 63：`scripts/deploy-hf.sh` + HF Secrets 注入（JWT / WX / AI / 七牛 / Supabase）
2. `Dockerfile` / `docker-entrypoint.sh` 适配：持久盘挂 `POSE_MODEL_PATH` 与临时帧目录；entrypoint 顺序保持（`alembic upgrade head` → uvicorn）
3. 灰度切流：先 Admin 后小程序；**魔搭保留为回滚目标**，稳定运行一个版本周期后再下线
4. 收尾：`deploy-server-modelscope.yml` → `.github/workflows-disabled/`，更新方案 65 状态
5. ⏪ 回滚：反代切回魔搭（配置在项目外，秒级）

**反代契约（供项目外配置方参考）**：HTTPS；透传 `X-Auth-Token`（勿占用 `Authorization`，见方案 66）；`/api/upload/*` 与 SSE `text/event-stream` 不缓冲；`Range` 头透传；请求体上限 ≥ `MAX_UPLOAD_SIZE_MB`；超时 ≥ 管线时长。

**验收**：真机三端回归 + 连续观察一周无 5xx / 无冷启动超时。

### 顺序与禁令

- **串行**：阶段一 → 阶段二 → 阶段三，不可并行；**禁止** DB 与存储同期替换（变量过多、回滚困难）。
- 每阶段开工前，人类确认前置凭据就绪；每阶段完成后按 AGENTS 4.3 验证再提交。
