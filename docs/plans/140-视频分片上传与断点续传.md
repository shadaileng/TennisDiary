# 140 视频分片上传与断点续传（137 阶段二）

影响面：`server/app/services/file_store.py`、`server/app/services/file_service.py`、`server/app/routers/upload.py`、`server/app/routers/admin/files.py`、`server/tests/*`；`miniapp/src/utils/chunkUpload.ts`（新增）、`miniapp/src/utils/crc32.ts`（新增）、`miniapp/src/utils/upload.ts`、`miniapp/src/services/data.ts`、`miniapp/src/pages/coach/analyze.vue`

> 本方案是 [137](./137-视频上传两步秒传.md) §六「阶段二：分片上传 + 断点续传（独立交付）」的展开，
> 阶段一（秒传两步 + 上传/分析进度体验）已落地并保持不动，本文只新增分片链路。

## 一、需求

1. 大视频（数十~上百 MB）弱网下整体上传失败率高，失败后必须整包重传。
2. 分片上传：按固定大小切片，单片失败只重传单片。
3. 断点续传：上传中断（取消 / 退后台 / 杀进程 / 失败重试）后再次发起，仅上传服务端**缺失或已失败**的分片。
4. 交付物与阶段一完全一致 —— **最终只拿到 `file_id`**，后续 `/api/analyses/start` 流程零改动。
5. 小文件不引入额外往返：低于阈值仍走 `/api/upload/video` 整体上传。

## 二、现状与问题

### 2.1 阶段一链路（已落地，保持不变）

`miniapp/src/pages/coach/analyze.vue` → `resolveVideoFileId()`：

```
getFileFingerprint()（md5 + size）
  → POST /api/upload/check {md5, size_bytes, category:"video"}
      ├─ hit + safe → file_id
      └─ miss / 异常 → POST /api/upload/video（整包 multipart，带进度/超时/取消）→ file_id
  → POST /api/analyses/start {file_id, ...}
```

| 项 | 现状 | 分片后 |
|---|---|---|
| 失败成本 | 90% 处失败 = 全量重传 | 仅重传失败单片 |
| 中断续传 | 不支持（重传整包） | 支持（`md5` 为 key，24h 内可续） |
| 服务端内存 | `file.file.read()` 整包读入（100MB 峰值） | 单片 5MB |
| 进度粒度 | `onProgressUpdate` 实时字节 | 片级进度（已传片数 + 当前片字节） |
| 超时 | `resolveUploadTimeout(size)` 自适应（120~300s） | 单片固定短超时（按片大小） |

### 2.2 必须适配的既有约束（代码事实）

## 三、关键决策

| # | 决策 | 说明 |
|---|---|---|
| 1 | 客户端切片：`FileSystemManager.readFile({filePath, position, length})` 读 ArrayBuffer → `writeFile` 写临时分片文件 → `uni.uploadFile` 上传（multipart） | `position`/`length` 自基础库 **2.10.0** 起支持，`[position, position+length)` 左闭右开；不传 `encoding` 时返回 ArrayBuffer（微信官方文档已核实） |
| 2 | **不采用** `uni.request` 直传 ArrayBuffer | `wx.request` 的 `data` 对 ArrayBuffer 的支持与基础库要求不明确，且**无上传进度回调**、无法 `abort()`；写临时文件虽多一次本地 IO（5MB），但可完整复用阶段一的进度/取消能力 |
| 3 | 传输层沿用 multipart，不引入 raw octet-stream | 与现有上传端点一致，后端 `UploadFile` 直读，无需改造请求解析 |
| 4 | **分片会话 = 单文件 `data.bin` + 状态登记文件 `manifest.json`**，不建表、不加迁移 | 目录 `UPLOAD_DIR/tmp/chunks/<uid>/<md5>/`；`data.bin` 按 `offset` 定位写、天然就是最终形态；`manifest.json` 是唯一权威真源（`segments` 记录每段成败）。引入 DB 会显著增加复杂度且需清理事务 |
| 5 | 全部分片 IO 落 `file_store`（物理层），语义与入账由门面 `file_service` 负责 | 满足 138 架构守卫；路由零磁盘操作；`file_store` 只提供 `pwrite` / manifest 原子读写等原语，`ok`/`failed` 判定归门面 |
| 6 | complete 必须服务端重算 MD5 + size 并与客户端比对，不一致 409 | 客户端 MD5 不可信；整体校验是唯一可靠的完整性保证（本次免合并，`data.bin` 本就是完整文件） |
| 7 | **写盘成功且片级校验通过 → 才入账 `ok`；失败（校验不过或写异常）→ 入账 `failed` 并返回 400** | 以 manifest 为唯一真源，杜绝「manifest 说写了但磁盘没有」的倒挂；失败段入账使客户端可精确只重传该段 |
| 16 | 定位写用 `os.pwrite(fd, data, offset)`，**不做预 `truncate`** | `pwrite` 不移动共享文件指针，多个写者各写各段天然安全（为后续并发预留，当前串行零成本）；不预分配则文件随最大已写 offset 自然增长，避免稀疏文件在部分文件系统上被实际填零 |
| 17 | 单片写盘后 `os.fsync(fd)` 再入账 | 「写成功才入账」的落点：不 fsync 则掉电可能出现「已入账但区段是空洞」 |
| 18 | manifest 采用**原子写**：写 `manifest.json.tmp` → `os.replace` | 防止进程中断留下半截 JSON 使整个会话不可读；`os.replace` 同目录内原子 |
| 19 | 片级校验 = `length` 强制 + `crc32` 可选 | 服务端按 manifest 自算 `expect` 长度，`len(content)` 不符即失败（拦住截断/半包这一主要故障模式）；`crc32` 由客户端随片携带，服务端 `zlib.crc32` 复核，拦住内容损坏。纯 JS 的 CRC32 比 MD5 快一个量级（见决策 21），故片级用 CRC32、整文件仍用 MD5 |
| 20 | 客户端新增 `utils/crc32.ts`（表驱动，纯 TS 零依赖） | 小程序端无 ArrayBuffer 摘要 API（`getFileInfo` 只对整文件算 MD5），且纯 JS MD5 在 100MB 量级耗时数秒不可接受；CRC32 表驱动约 5MB/30~60ms，20 片累计 <1.5s，且可开关降级（算失败/超时则不传 `crc32`，退化为仅长度校验） |
| 21 | complete 失败（409）时**按 manifest 标记重传范围**：有片级 `crc32` 的段可保留，其余段清 `ok` 标记 | 有 `crc32` 的段已在分片阶段证明内容正确，整文件 MD5 不符只可能是极罕见的写后损坏或客户端切片/指纹错误；无 `crc32` 的段无法定位，只能整包重传（与阶段一行为一致，不退化）。**防死循环**：若客户端整文件 MD5 本身算错，局部重传永远对不上——前端对 409 只允许按 `missing` 局部重传 1 次，再次 409 直接降级整体上传 |
| 22 | 分片仍**串行**上传，但写入结构按并发设计 | 小程序并发请求上限 10，串行可保证进度单调、服务端内存可控；`pwrite` + 段级状态使将来改并发**零结构变更**（见 §3.1 与 §九） |
| 8 | 阈值/片大小由服务端下发（`/upload/check` 响应 `chunk` 字段），前端仅做缺省兜底 | 服务端单一真源，后续可接入 78 配置注册表在线调整，不必发版 |
| 9 | 单片 **5MB**；`size >= 20MB` 才走分片；`MAX_CHUNK_COUNT=512` | 100MB 视频 = 20 片；往返次数可控，单片重试代价小；512 片对应 2.5GB 理论上限，实际由 `MAX_UPLOAD_SIZE_MB` 截断 |
| 10 | 单片**串行**上传 + 单片失败重试 2 次（退避 1s / 2s） | 小程序并发请求上限 10，串行可保证进度单调、服务端内存可控、弱网下单片超时不互相拖累；并发留作后续优化 |
| 11 | 取消沿用阶段一：`uploadCanceled` 标志 + 当前片 `task.abort()` | 每片上传前检查标志，`onTask` 回调中若已取消立即 abort；已传分片保留，取消后可直接续传 |
| 12 | 分片路由**不打审计**，`/complete` 保留 `@audit(action="UPLOAD", resource_type="upload")` | 分片高频（20~40 次/视频）会淹没审计库；只有 complete 代表一次业务意义上的上传完成 |
| 13 | 临时目录纳入 `_SKIP_SCAN_DIRS`，并新增过期清理（24h）接入 Admin 清理端点 | 避免 Admin 文件扫描出现大量孤儿分片；complete 成功后立即删除目录 |
| 14 | 秒传优先级最高：分片前必先 `/upload/check`，命中直接返回 `file_id` | 与阶段一一致，命中场景零流量、零分片 |
| 15 | 视频安全检查沿用 137 决策 3 | 微信三件套不支持视频 → complete 成功后 `mark_security_checked(True)` |

### 3.1 备选方案裁决（归档）

分片「如何落盘与记账」共评估过三个形态，结论记录在案，避免日后重复推导。

| 方案 | 形态 | 结论 |
|---|---|---|
| **A** | 每片一个 `.part` 文件，complete 按序合并 | ❌ 排除 |
| **B** | 单文件偏移写（BT 式），**无**状态登记文件 | ❌ 排除 |
| **C+** | **单文件偏移写 + `manifest.json` 权威登记 + 片级校验**（本方案） | ✅ 采纳 |

**A 被排除的理由（修正过的判断）**

- 早期判断认为 A「目录里 `.part` 的客观存在 = 可靠记账」，这一条**不成立**：`.part` 存在只证明「写过」，不证明「内容正确」。网络截断、字节数对不上的分片照样能落成一个 `.part`。
- 因此在「内容必须可靠」这一前提下，**A 与 C 一样需要片级校验**，A 并不免费；加了片级校验后，A 与 C 的可靠性等价，差异只剩工程形态。
- 形态上 A 更弱：①中间产物 N 个文件（100MB → 20 个，磁盘峰值 = 分片 + `merged` 两份）；②complete 必须额外做一次合并 IO；③**A 是「串行顺序 append」的特化实现，不具备并发扩展能力**——将来要多路并发灌同一文件，等于推倒重写成 C。

**B 被排除的理由**

- B 省掉 manifest，靠「文件本身」判断进度。但本协议**没有 per-chunk hash 契约**（客户端只提供整文件 MD5），服务端无法区分某区段是「未写的空洞」还是「写坏的垃圾」，断点续传就无从判断缺哪段。
- 要补上这个能力，服务端必须自建「区段 bitmap + 区段完整性证明」，等于把 BT 协议层免费提供的能力自己实现一遍，复杂度反而高于写一个 manifest。

**C+ 被采纳的理由**

1. **可靠性闭环自洽**：以 manifest 为唯一权威真源，写盘 + 片级校验 + fsync 全部成功才入账 `ok`，不存在「记账说写了但磁盘没有」的倒挂；失败段入 `failed`，客户端精确重传该段。
2. **中间产物最少**：全程只有 1 个 `data.bin`，无合并步骤、磁盘峰值只有 1 份文件大小；complete 时 `register` 直接把 `data.bin` 移入受管路径。
3. **并发扩展零重构**：`pwrite` 定位写 + 段级状态天然支持 N 个写者各写各段；将来从串行改并发，只需给 manifest 写入加一把锁 + 客户端并发调度，存储结构一字不改。
4. **成本已在可控范围**：相对 A 多出的仅是 manifest 原子写与片级 CRC32，均属一次性实现成本，且 CRC32 是可选降级项。

## 四、方案设计

### 4.1 整体时序

```
选择视频（chooseMedia）→ 预计算指纹（md5 + size）
   │
   ▼
POST /api/upload/check {md5, size_bytes, category:"video"}
   │
   ├─ hit + safe ─────────────────────────────→ file_id ─┐
   │                                                     │
   └─ miss：响应附带 chunk 策略 + uploaded[]              │
        │                                                │
        ├─ size < threshold → POST /upload/video（整包）─┤
        │                                                │
        └─ size >= threshold → 分片流程 ↓                │
              for i in missing(uploaded[], failed[]):     │
                readFile(position=i*5MB, length)          │
                  → crc32(buffer)（可选，失败则不带）      │
                  → writeFile(tmp)                        │
                  → POST /upload/video/chunk              │
                      {file, md5, index, length, crc32?}  │
                      （首片带 total/size_bytes/original_name 建会话）
                      （片级校验失败 400 → 该片重试 2 次）
                  → unlink(tmp)                           │
              服务端每片：pwrite(data.bin, offset=i*5MB)   │
                  → fsync → 校验通过入 manifest.ok         │
                  → 校验失败入 manifest.failed → 400       │
              POST /upload/video/complete {md5, size_bytes?}
                → 段齐全? → md5_and_size_of(data.bin)
                → 校验 md5/size → register(移动 data.bin)
                → mark_security_checked → 清临时目录
                                                          │
                                                          ▼
                                                        file_id
                                                          │
                                    POST /api/analyses/start {file_id, ...}
```

### 4.2 会话的物理形态

```
UPLOAD_DIR/tmp/chunks/<user_id>/<md5>/
├── data.bin            # 最终完整文件的唯一载体：各片按 offset 定位写入（空洞由 OS 补零）
└── manifest.json       # 权威状态登记（原子写）：段成败、总长、片大小、原始名、时间戳
```

`manifest.json` 结构（`v=1`）：

```json
{
  "v": 1,
  "md5": "客户端整文件 md5（小写 32 hex）",
  "total_size": 104857600,
  "chunk_size": 5242880,
  "total": 20,
  "ext": ".mp4",
  "original_name": "clip.mp4",
  "segments": {
    "0": { "state": "ok",     "size": 5242880, "crc32": "9a1b2c3d", "at": "2026-09-09T10:00:00Z" },
    "5": { "state": "failed", "size": 0, "reason": "crc_mismatch", "at": "2026-09-09T10:00:12Z" }
  },
  "created_at": "2026-09-09T09:59:58Z",
  "updated_at": "2026-09-09T10:00:12Z"
}
```

- `segments` 的 key 是分片索引（字符串）；`state` 仅 `ok` / `failed` 两态；
- 派生视图：`ok` 列表 = 续传可跳过的片，`failed` + 未登记 = 需要（重）传的片；
- 段级记录使「只重传失败段」成为服务端可表达的事实，而不是客户端猜测。

**会话定义与生命周期**

- **一个会话 = 一个 `md5` 的同一文件上传任务**，唯一标识为 `(user_id, md5)`，与 HTTP 请求次数、与用户「点击上传」的次数均无关；
- 会话是**首片懒创建**：前端无需显式「开一个会话」，首个待传片携带 `total` / `size_bytes` / `original_name`，服务端 `open_chunk_session` 无 manifest 则写一份；已有则校验关键字段一致后**幂等复用**（保留已入账段）——这也是断点续传无需前端感知「旧会话存在」即可继续的根本原因；
- **一次上传自始至终只对应一个会话**：首片建 → 后续片仅 `_mark_segment` 追加入账 → complete 校验后 `register` 迁走 `data.bin` 并 `clear_chunks` 销毁；
- 中途取消 / 断网 / 失败会**残留会话目录**（同 md5 再次上传即复用续传），超过 24h 无进展由 `cleanup_expired_chunks` 回收；complete 成功后旧会话已销毁，同 md5 再次上传会新建会话。

**`data.bin` 的大小形态（不是拼接出来的）**

- 各片经 `os.pwrite` **直接定位写入自身偏移** `offset = index * chunk_size`，全程没有独立临时分片文件、也没有 complete 合并动作；`data.bin` 本身就是最终文件的原位副本，complete 是「免合并」直接校验后 `register` 迁移到 `videos/<uid>/<md5><ext>`；
- **文件大小并非一开始就等于 `total_size`**，而是「随已写入的最大偏移生长」：顺序传片时文件随片逐渐长到总大小；乱序或续传先写了高 offset 片时，中间空洞由 OS 自动补零并把文件撑到该 offset——因此**中途看到 `data.bin` 大小已等于最终文件，通常意味着已写到靠近尾部的区段（或所有片已传完），并不代表文件完整**；
- 判断上传进度的权威依据**不是文件大小**，而是 `manifest.json` 里 `segments` 的 `ok` 集合。

```python
CHUNK_DATA_NAME = "data.bin"                 # 单文件载体

def write_manifest(user_id: int, md5: str, manifest: dict) -> None: ...
    # 写 manifest.json.tmp → os.replace 原子替换（同目录内原子，杜绝半截 JSON）
def clear_chunks(user_id: int, md5: str) -> int: ...           # 删除整个 md5 目录，返回删除文件数
def cleanup_expired_chunks(max_age_hours: int = 24) -> int: ...
    # 遍历 tmp/chunks/*/*，按 manifest.updated_at（缺失则回退目录 mtime）超期整体删除
```

要点：

- 存储层**只做物理动作**（定位写、原子读写 JSON、删目录），不含 `ok`/`failed` 语义与任何校验判定；
- `pwrite` 不依赖共享文件指针，为将来多写者并发预留（现在串行也用同一函数，零额外成本）；
- 所有路径经 `ensure_dir` / `abs_of`，不做字符串拼接写盘（满足守卫）。

### 4.4 门面新增（`file_service.py`）

```python
CHUNK_SIZE_BYTES = 5 * 1024 * 1024
CHUNK_THRESHOLD_BYTES = 20 * 1024 * 1024
MAX_CHUNK_COUNT = 512
CHUNK_MANIFEST_VERSION = 1
_MD5_RE = re.compile(r"^[0-9a-f]{32}$")

class ChunkParamError(ValueError): ...        # → 400 参数非法
class ChunkSessionError(ValueError): ...      # → 400 会话不存在（要求客户端先传首片建会话）
class ChunkVerifyError(ValueError): ...       # → 400 片级校验失败（length/crc32 不符），已入 failed
class ChunkIncompleteError(ValueError): ...   # → 400 缺片（含 missing 列表）
class ChunkMismatchError(ValueError): ...     # → 409 整文件 md5/size 不符
class ChunkTooLargeError(ValueError): ...     # → 413 超过 MAX_UPLOAD_SIZE_MB

def chunk_policy() -> dict:
    """{enabled, size_bytes, threshold_bytes, max_count, crc32}（供 /upload/check 下发）"""

def validate_chunk_params(md5: str, index: int, total: int) -> None:
    """md5 小写 32 hex、0<=index<total、1<=total<=MAX_CHUNK_COUNT"""

def open_chunk_session(
    user_id: int, md5: str, *, total_size: int, chunk_size: int = 0,
    total: int = 0, original_name: str = "", ext: str = "",
) -> dict:
    """幂等创建/复用会话：无 manifest 则写一份；已存在则校验关键字段一致后复用，不一致抛 ChunkParamError"""

def register_chunk(
    user_id: int, md5: str, index: int, content: bytes, *, length: int = 0, crc32: str = "",
) -> dict:
    """片级校验 → pwrite → fsync → 入账 ok/failed → {index, size, ok, failed, missing}"""

def list_chunks(user_id: int, md5: str) -> dict:
    """{ok: [...], failed: [...], missing: [...], chunk_size, total, total_size, crc32}"""

def complete_chunk_upload(
    db: Session, user_id: int, *, md5: str, size_bytes: int = 0,
) -> tuple[File, bool]:
    """段齐全校验 → 整文件 MD5 → register（返回 (File, reused)）"""

def cleanup_expired_chunks(max_age_hours: int = 24) -> int: ...
```

`register_chunk` 内部流程（**顺序不可调换**：先校验、再写盘、最后入账）：

1. 读 manifest；不存在 → `ChunkSessionError`（客户端需从 index=0 重开会话）；
2. 参数校验：`0 <= index < manifest.total`；单片 `len(content) <= CHUNK_MAX_BYTES`；
3. `offset = index * manifest.chunk_size`；`expect = min(chunk_size, total_size - offset)`；
   `len(content) != expect` → 记 `failed{reason:"length_mismatch"}` 并抛 `ChunkVerifyError`；
4. 若客户端带 `crc32`：`zlib.crc32(content) != int(crc32, 16)` → 记 `failed{reason:"crc_mismatch"}` 并抛 `ChunkVerifyError`；
5. `file_store.pwrite_chunk(...)`（内部 `pwrite` + `fsync`）；抛异常 → 记 `failed{reason:"write_error"}` 并抛 `ChunkVerifyError`；
6. **写盘成功后**入账 `segments[str(index)] = {state:"ok", size, crc32, at}`，`updated_at` 刷新 → `write_manifest`（原子写）；
7. 返回 `{index, size, ok, failed, missing}`（后三者由 manifest 派生，客户端据此推进进度与续传）。

> 失败路径同样要落 manifest（`failed` 入账），但若 `write_manifest` 自身失败（磁盘满等）：仅 `log.error` 记录并返回 500，
> 不改写内存态——下次请求会重读 manifest，最坏退化为「该段需重传」，不会污染已入账的其它段。

> 幂等：重复上传同一 `index`（内容相同）会重新 `pwrite` 同一区段并覆盖入账，结果一致；`ok` 集合不重复计数。

`complete_chunk_upload` 内部流程：

1. 读 manifest；不存在 → `ChunkSessionError`；
2. `ok` 段数 != `total`，或 `data_size(...) != total_size` → `ChunkIncompleteError`（错误信息附 `missing` 数量与前若干索引，便于排障）；
3. `real_md5, real_size = file_store.md5_and_size_of(chunk_data_abs(...))`（**免合并**：`data.bin` 已是完整文件）；
4. `real_md5 != manifest.md5` 或（`size_bytes > 0` 且 `real_size != size_bytes`）或 `real_size != total_size`
   → 按决策 21 清 `ok` 标记（保留有 `crc32` 的段）→ `ChunkMismatchError`；
5. `real_size > MAX_UPLOAD_SIZE_MB * 1MB` → `clear_chunks` + `ChunkTooLargeError`；
6. `record, reused = register(db, user_id, src_path=data_abs, category="video", original_name=manifest.original_name, ext=manifest.ext)`；
   （`register` 内部 `move_into_place` 把 `data.bin` 迁入 `videos/<uid>/<md5><ext>`，无额外拷贝）
7. `mark_security_checked(db, user_id, record.rel_path, True)`；
8. `file_store.clear_chunks(user_id, md5)`（此时 `data.bin` 已被移走，仅清理目录与 manifest）；`db.commit()`；
9. 返回 `(record, reused)`。

> 幂等：同用户重复 complete 同一 MD5 → `register` 命中既有记录，返回同一 `file_id`，`reused=True`；
> 复用命中时 `register` 会删除临时源，再 `clear_chunks` 兜底。

#### `miniapp/src/utils/crc32.ts`（新增）

#### `miniapp/src/utils/chunkUpload.ts`（新增）

```ts
export interface ChunkPlan {
  enabled: boolean;
  sizeBytes: number;      // 单片大小（缺省 5MB）
  thresholdBytes: number; // 分片阈值（缺省 20MB）
  maxCount: number;       // 512
  crc32: boolean;         // 服务端是否接受片级 crc32（缺省 true）
  total: number;          // 服务端会话已知总分片数（首次为 0）
  totalSize: number;      // 服务端会话已知总字节（首次为 0）
  chunkSize: number;      // 服务端会话片大小（首次为 0）
  uploaded: number[];     // ok 段（可跳过）
  failed: number[];       // failed 段（需重传）
  missing: number[];      // 未登记段（需上传）
}

export function computeChunkCount(sizeBytes: number, chunkSize: number): number; // ceil，至少 1

export interface ChunkedUploadParams {
  filePath: string;
  md5: string;
  size: number;
  originalName: string;
  plan: ChunkPlan;
  onProgress?: (p: { percent: number; done: number; total: number }) => void;
  onChunkTask?: (task: UniApp.UploadTask) => void;   // 供取消时 abort 当前片
  isCanceled?: () => boolean;
  onEvent?: (name: string, payload?: Record<string, unknown>) => void; // 埋点
}

export async function uploadVideoChunked(params: ChunkedUploadParams): Promise<number>; // 返回 file_id
```

内部实现：

| 步骤 | 实现 |
|---|---|
| 待传集合 | `pending = unique([...missing, ...failed])`，`missing` 为空时按 `total` 自行推导；升序串行处理 |
| 读片 | `fs.readFile({filePath, position: i * size, length: size})`，不传 `encoding` → ArrayBuffer |
| 片级摘要 | `plan.crc32` 为真时 `crc32Of(buffer)`；异常则本次不带 `crc32`（服务端退化为长度校验） |
| 落临时文件 | `fs.writeFile({filePath: ${wx.env.USER_DATA_PATH}/td_chunk.part, data: buffer})`；串行复用同一路径 |
| 上传 | `uploadRaw({path:"/upload/video/chunk", filePath: tmpPath, fieldName:"file", formData:{md5, index:String(i), length:String(len), crc32?, // 首片追加 total/size_bytes/original_name }, timeout: resolveUploadTimeout(chunkSize), onTask, onProgress})` |
| 清理 | `try/finally` 内 `fs.unlink({filePath: tmpPath})`（失败仅 warn，不阻断） |
| 重试 | 单片失败（含 400 片级校验失败）重试 2 次（退避 1s / 2s）；三次全败 → 抛错（已传段保留在服务端，下次续传只补这些段） |
| 取消 | 每片开始前 `isCanceled?.()` 立即中断；`onChunkTask` 中若已取消则 `task.abort()` |
| 进度 | `percent = round((done + curPercent / 100) / total * 100)`，回调 `{percent, done, total}` |
| 完成 | `POST /upload/video/complete {md5, size_bytes}` → `file_id`；409 → 用响应 `missing` 局部重传一次，仍失败则抛错（调用方降级整体上传） |

前端「感知进度」拆成**两个层次**，职责不同、互不冲突（manifest 只在服务端内部被读取，前端拿到的是派生的三集合）：

| 层次 | 数据来源 | 触发时机 | 作用 |
|---|---|---|---|
| **真实续传进度** | 服务端 manifest → `ok`/`failed`/`missing` 三集合（经 `/upload/check` 的 `chunk` 或 `GET /video/chunks`；409 后走 `fetchChunkProgress`） | 上传开始前 + 409 局部重传前（每视频仅 1~2 次） | `resolvePending` 只挑 `failed + missing` 作为待传集，`done` 起始 = `skipped`（已跳过片数），`skipped > 0` 时打 `video_chunk_resume` 埋点 |
| **上传过程实时进度** | 本地 `done` / `total` 计数（`emit` 自算） | 每片成功后 `done += 1` 回调一次 | `percent = round((done + cur/100) / total * 100)` 平滑推进进度条与「已传 n/m 片」文案 |

> 不在每片上传后实时拉取 manifest——那是服务端内部真源，逐片轮询会把请求数翻倍；真实续传点只在开传/重试边界取一次权威值，显示层用本地计数即可，两者各司其职。

> 兜底：`readFile` / `writeFile` 在个别机型或超大文件（微信文档标注单文件上限 100MB）失败时，
> `chunkUpload` 抛出可识别错误，`resolveVideoFileId` 捕获后**静默降级为整体上传**（埋点记录）。

### 4.8 清理与运维

| 项 | 实现 |
|---|---|

## 八、风险与注意事项

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| `readFile` 单文件上限 100MB（微信文档标注） | 超大视频切片读取失败 | 分片前判 `size`；`readFile` 失败 → 静默降级整体上传 + 埋点 `video_chunk_degraded`；真机验证 100MB+ 场景 |
| 本地临时分片占用 `USER_DATA_PATH` 空间 | 小程序本地配额 | 单片 5MB 串行复用同一路径，`try/finally` 必删；异常路径 warn 不阻断 |
| 分片残留占磁盘 | 磁盘增长 | complete 即清；24h 过期清理；Admin `/cleanup` 联动；`scan` 豁免避免误报 |
| 请求次数放大（100MB → 20 次请求） | 网关 QPS / 总体耗时上升 | 串行 + 短单片超时；阈值 20MB 以下不分片；如需提速直接上多并发（`pwrite` 结构已就绪，见 §九） |
| 客户端 MD5 与服务端不一致 | complete 409，需重传 | 与阶段一一致（全文件 MD5、原样上传）；409 时按响应 `missing` 局部重传一次，仍失败则降级整体上传 |
| 同一用户多会话同时上传同一 MD5 | 会话目录竞争（manifest 双写） | 当前串行模式：同名区段 `pwrite` 覆盖（内容相同，幂等），complete 幂等返回同一 `file_id`；**多并发前必须给 manifest 写入加文件锁**（§九） |
| 审计装饰器为同步 wrapper | 分片路由若改 `async` 会静默失效 | 分片路由一律 `def`（同步），单片 5MB 无性能问题 |
| `data.bin` 空洞未写满即被 complete | 文件被空洞填零，MD5 必不符 | complete 前强制校验 `ok` 段数 == `total` 且 `data_size == total_size`，缺一即 400 |
| 稀疏文件在部分文件系统被实际分配 | 磁盘占用 = `total_size` | 不做预 `truncate`，文件随最大已写 offset 增长；100MB 上限下影响可控 |
| 单片 `fsync` 开销 | 单片耗时略增 | 5MB fsync 为毫秒级；换来「写成功才入账」的可靠性，不做开关 |
| 客户端 CRC32 计算耗时 | 弱端机上传前耗时增加 | 100MB 累计约 0.6~1.2s；可关闭（`chunk.crc32=false` 或计算异常自动跳过），退化为长度校验，不影响主流程 |
| 魔搭 / Cloudflare 代理请求体限制 | 上传被拒 | 单片 5MB 远低于代理与网关请求体上限（Workers 免费版 100MB），无影响 |
| `MAX_UPLOAD_SIZE_MB = 100` | 大于 100MB 的视频被拒 | 当前配置值；若业务需要更大，改 78 配置注册表 `data.max_upload_size_mb`（无需发版） |
| 分片目录未加入扫描豁免 | Admin 文件扫描出现大量孤儿 | Step 2 必须同步改 `_SKIP_SCAN_DIRS`，并补一条扫描用例 |

## 九、后续可选（不在本期）

- **多路并发分片（2~3 路）**：存储结构已就绪（`pwrite` 定位写 + 段级状态），只需 ①manifest 写入加文件锁（或按段分片写后再合并入账）②客户端并发调度与进度聚合 ③单片失败段的并发重试——**不需要改动存储格式**
- 片级摘要升级为 MD5 / BLAKE3（当前 CRC32 已足够检错，升级仅在需要抗恶意篡改时考虑）
- 本地持久化续传进度（Storage 记录 `md5 → ok[]`，省去一次查询）
- 图片分片（装备封面/头像均 <1MB，当前无必要）

## 十、问答记录（FAQ）

> 实施与联调阶段沉淀的常见疑问，用于机制澄清与排障。相关正文见 §4.2（会话与 `data.bin`）、§4.4（complete）、§4.6（进度感知）。

### Q1：`data.bin` 不是一开始就和最终文件一样大吗？是后续拼接出来的吗？

不是拼接。`data.bin` 是最终文件的**原位副本**：

- 每个分片经 `os.pwrite` 直接定位写入自己的偏移 `offset = index * chunk_size`，全程没有独立临时分片、也没有 complete 合并；
- 文件大小**随已写入的最大 offset 生长**：顺序传片时逐渐长到总大小；乱序/续传先写高 offset 片时，中间空洞由 OS 补零并直接把文件撑到该 offset；
- 因此看到「`data.bin` 已和最终文件一样大」，通常意味着已写到靠尾部区段（或片已传完），**不代表文件完整**——判断进度要以 `manifest.json` 的 `ok` 段集合为准，而不是文件大小。

### Q2：只传了两片、大小 10MB，正常吗？重新上传会从第三片开始吗？

- **正常**：单片大小 = `CHUNK_SIZE_BYTES = 5MB`，两片定位写后文件被撑到 10MB，`data.bin` 此时只是「长到 10MB」，并不完整；
- **断点续传（同 `md5`）→ 会从第 3 片（index=2）开始**：再次上传前 `/upload/check` 下发 `missing`，`missing = [i for i in range(total) if i not in ok_set]`，前两片已在 `ok`，前端 `resolvePending` 只传 `missing + failed`；
- **判定依据**：以服务端 manifest 的 `ok` 段为准。同 `md5` 且会话未 complete/未过期 → 续传（从 `missing` 首段起）；换 `md5`、会话已 complete 销毁或超过 24h 被清理 → 全新会话从头传。

### Q3：会话是怎么定义的？一次上传一个会话吗？

- **一个会话 = 一个 `md5` 的同一文件上传任务**，唯一标识 `(user_id, md5)`，物理形态为目录 `UPLOAD_DIR/tmp/chunks/<user_id>/<md5>/` 下的 `data.bin` + `manifest.json`；
- **一次上传自始至终只对应一个会话**，但会话是**首片懒创建**：前端不显式开会话，首个待传片带 `total`/`size_bytes`/`original_name`，服务端 `open_chunk_session` 幂等创建；后续片只入账不建会话；complete 后 `register` 迁走 `data.bin` 并 `clear_chunks` 销毁目录；
- 中途取消/断网会**残留目录**，同 `md5` 再次上传即复用续传；超过 24h 无进展被 `cleanup_expired_chunks` 回收（接入 Admin `/cleanup`）；
- 简言之：**不是「每次点击一个会话」，而是「每个文件（按 user_id + md5）一个会话」，从首片自动创建到 complete 自动销毁**。

### Q4：manifest 在哪些端点被读取？前端如何感知当前进度？

**manifest 只在服务端内部读取**（唯一入口 `file_store.read_manifest`），经三个门面消费、三个端点暴露：

| 门面消费点 | 读取目的 | 暴露端点 |
|---|---|---|
| `open_chunk_session` | 已有会话时校验参数一致后幂等复用 | `POST /upload/video/chunk`（首片） |
| `list_chunks` → `_summary` | 派生 `ok`/`failed`/`missing` 三集合 | `GET /upload/video/chunks`、`/upload/check` 的 `chunk` |
| `_require_session` | 片级校验/写盘/入账、complete 段齐全校验 | `POST /upload/video/chunk`（每片）、`POST /upload/video/complete` |

前端**拿不到原始 manifest**，只拿派生的三集合；进度感知分两层（详见 §4.6）：

- **真实续传进度**：开传前/409 重试前读一次 `/upload/check`（或 `fetchChunkProgress`）拿到 `uploaded`/`failed`/`missing`，决定传哪些片、统计 `skipped`；
- **上传过程实时进度**：本地 `done`/`total` 计数自算百分比（每片成功后回调一次），不在每片后实时拉 manifest（避免请求翻倍）。

> 排查建议：看到 `data.bin` 大小异常或续传行为不符预期时，直接查看该会话目录的 `manifest.json` —— `segments` 里每个索引的 `state`（`ok`/`failed`）与 `at` 时间戳即服务端唯一真源，能准确回答「已传哪些片、下一个该传哪片」。
