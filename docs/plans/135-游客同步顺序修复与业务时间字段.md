# 游客同步顺序修复与业务时间字段

## 1. 问题描述

小程序端游客模式创建日记/装备/体重后，登录同步到云端，数据的 `created_at` 时间戳不反映真实创建顺序。

### 1.1 根因分析

```
游客创建顺序（时间线）：  A(10:00) → B(10:05) → C(10:10)
                           ↓ 存储（unshift 头插）
本地数组顺序：            [C, B, A]  （最新在前）
                           ↓ 同步上传顺序
服务器 created_at：       C(T1) → B(T2) → A(T3)
                           ↓ API 返回 created_at DESC
最终展示顺序：            A → B → C  ← 顺序反转！
```

**核心问题**：
1. `pendingRepo.ts` 使用 `list.unshift(item)` 头插法，新数据在数组最前面
2. `sync.ts` 按数组顺序逐条上传，服务器用 `time.time()` 赋值 `created_at`
3. 最旧的数据最后上传，获得最新的 `created_at`，导致排序反转

### 1.2 影响范围

- 日记列表排序错误
- 装备列表排序错误
- 体重列表排序错误
- Admin 后台看到的创建时间不是真实创建时间

## 2. 解决方案

### 2.1 方案概述

新增 `business_time` 字段（Float，UTC Unix 时间戳），记录用户真实创建时间。`created_at` 保持"入库时间"语义不变。

### 2.2 字段设计

| 字段 | 类型 | 说明 | 示例 |
|------|------|------|------|
| `created_at` | Float | 服务器入库时间（`time.time()`） | 1725532800.0 |
| `business_time` | Float \| Null | 用户真实创建时间（`Date.now()/1000`） | 1725529200.0 |

- 游客同步时：`business_time` = 本地 `createdAt`（原始创建时间戳）
- 正常创建时：`business_time` = `null`（直接走 API，`created_at` 即真实时间）
- 向后兼容：旧数据 `business_time = NULL`，前端 fallback 到 `date`/`time`

### 2.3 同步排序修复

在 `sync.ts` 中，对 pending 列表先按 `createdAt` 升序排序再上传，确保服务器 `created_at` 的相对顺序正确（双重保障）。
