# 137 视频上传两步秒传

影响面：`server/app`（routers/upload.py、routers/analyses.py、routers/video.py、services/file_service.py、services/file_store.py）、`miniapp/src`（pages/coach/analyze.vue、pages/coach/coach.vue、pages/coach/report.vue、services/analysisStatus.ts、utils/upload.ts、services/data.ts、manifest.json）

## 一、需求

> 小程序端视频上传使用两步方案，先检查是否命中秒传，否则再上传视频文件。
> 那就新增一个 `/upload/video` 端点，返回 `file_id` 给 `/api/analyses/start` 消费，这里拿到文件和以前的流程是一样的，不需要再新增 `POST /api/analyses/start-instant` 端点。

目标：同一视频重复分析时零流量上传；首次上传的可靠性与可观测性同步加固。

## 二、现状与问题

### 2.1 单步上传链路

`miniapp/src/pages/coach/analyze.vue` 的 `startAnalysisUnified()` 是唯一入口：

```
chooseMedia → uploadRaw({path:"/analyses/start", filePath, fieldName:"file", formData})
            → uploadRes.id（analysis_id）→ createStatusSubscriber → 跳报告页
```

| 问题 | 说明 |
|---|---|
| 重复上传浪费 | 同一视频换 `kind`/`cuts` 再次分析，仍要全量重传数十~上百 MB |
| 无上传进度 | `uploadRaw` 已封装 `onProgressUpdate`（`upload.ts:152`）但无调用方，上传期间界面无任何反馈 |
| 进度不醒目、可误操作 | 原实现只在底部一行小字显示百分比（`.analyze-progress`），且底层表单/时间轴仍可点击，上传与分析期间可触发其它操作 |
| 不可取消 | 上传发起后无任何中断入口，弱网下只能杀进程 |
| 超时偏紧 | 未传 `timeout`，`uploadRaw` 默认 60s；大视频弱网下必超时，且失败后无重试入口 |
| 无网络感知 | `uni.getNetworkType` 小程序端未使用，弱网场景无提示、无埋点 |
| `processing` 态无差异化展示 | 分析中退出页面后，列表与报告页对 `status=processing` 的记录渲染成「本地」/空报告，用户误判为分析失败（详见 §4.5） |

### 2.2 视频安全检查长期无效

`routers/video.py:243` 调用 `check_media_sync(abs_path, user_id, media_type=3)`。已核实微信官方文档
（`api_mediacheckasync.html`、`security.mediaCheckAsync-v1.html`）：

- `mediaCheckAsync` 的 `media_type` 仅支持 **1=音频 / 2=图片**，无视频类型 → 该调用实际返回 `errcode 40004`，被 `log.warning` 吞掉；
- 检测结果 30 分钟内推送到开发者消息接收服务器，**没有按 `trace_id` 查询结果的接口**，因此无法在上传请求中同步等待结论；
- 三件套（`imgSecCheck` / `msgSecCheck` / `mediaCheckAsync`）**均不支持视频**，平台也不要求对视频做检测。

结论：视频 `security_checked` 恒为 0 的根因即在此，本次改为「上传阶段直接视为放行」并清理死调用。

### 2.3 138 重构后的既有基础（必须适配）

| 项 | 现状 |
|---|---|
| 文件命名 | `{md5}.{ext}`，落盘 `UPLOAD_DIR/{avatars\|gears\|videos}/{user_id}/` |
| 同用户同 MD5 | 部分唯一索引 `uq_files_user_md5_active` → 永远只有一条有效记录 |
| 引用计数 | `file_bindings` 绑定表，经 `file_service.bind` / `unbind` / `rebind` 变更 |
| 路由约束 | `tests/test_file_architecture.py` 禁止路由出现 `uuid4(`、自写盘、`ref_count` 自增、直接 import File |
| `/upload/check` | `find_by_md5` + `exists` 三态，但**无 `file_id`、无来源隔离、无 size 校验** |
| `/api/analyses/start` | `file: UploadFile` + Form，`_save_uploaded_file` 内 `register`，随后 `bind(...,"analysis",analysis_id)`；**无测试直接调用该端点** |
| `/api/upload/video` | **不存在**（需新增） |

## 三、关键决策

| # | 决策 | 说明 |
|---|---|---|
| 1 | 新增 `/api/upload/video`，`/api/analyses/start` 凭 `file_id` 消费 | 不新增 `start-instant`；命中与未命中最终都只拿到 `file_id`，后续流程完全一致 |
| 2 | 预检复用 `/upload/check`，与图片同一流程 | 职责只做：是否命中 / 物理文件是否存在 / 是否通过安全检查；不按来源特判 safe |
| 3 | 安全检查只在**上传阶段**执行并写 `security_checked`，预检**只读** | 图片走 `check_image_sync`；视频无官方检测能力 → 上传阶段 `mark_security_checked(True)` |
| 4 | 清理无效 `check_media_sync(media_type=3)` 与 `check_media` / `check_media_sync` 死代码 | 见 2.2 |
| 5 | 每次分析仍生成新的 Analysis 记录与新报告 | 不做「同 md5 + 同参数复用旧报告」的报告级缓存 |
| 6 | 视频秒传走门面 `register` + `bind` | 138 后同用户同 MD5 唯一记录，`register` 幂等复用，不产生重复记录 |
| 7 | `/upload/check` 增加可选 `category` 做来源隔离 + `size_bytes` 一致性校验 | 修复装备封面可能命中头像记录返回 `avatars/...` 的隐患；不传时行为完全不变 |
| 8 | 降级优先 | MD5 超时 / 超大文件 / 预检异常 / `safe=false` 一律静默退回上传，仅埋点，不弹错 |
| 9 | 上传加固四项 + 分片断点续传 | 加固纳入阶段一；分片断点续传拆为阶段二独立交付 |
| 10 | 上传/分析期间**全屏模态遮罩**居中显示进度 | 醒目 + 阻断底部误操作；`@touchmove.stop.prevent`（编译为 `catchtouchmove`）防滚动穿透，点击遮罩不关闭 |
| 11 | 只开放**上传阶段取消**，分析阶段不提供取消 | 分析阶段取消会产生孤儿 Analysis 记录且后台管线无法中断；取消后保留 `videoPath` 与 MD5 指纹，可直接重试（重试仍先走秒传预检） |
| 12 | `processing` 态贯穿列表与报告页 | 列表：`⏳` 角标 + 「分析进行中…」+ 转圈，存在 processing 项时 4s 轮询；报告页：独立进度页 + 订阅状态，完成后自动重载完整报告 |
| 13 | 步骤文案单一真源 `stepLabel()` | `analyze.vue` 与 `report.vue` 共用 `services/analysisStatus.ts` 的映射，避免两处各写一份导致文案漂移 |

## 四、方案设计

### 4.1 整体时序

```
选择视频（chooseMedia）
  │
  ▼
getFileFingerprint()  ── 一次 getFileInfo 取 md5 + size（选后异步预计算）
  │
  ▼
POST /api/upload/check {md5, size_bytes, category:"video"}
  │
  ├─ hit=true, safe=true   → file_id ─────────────┐
  │                                               │
  ├─ hit=false / safe=false / 预检失败 / MD5 超时  │
  │        │                                      │
  │        ▼                                      │
  │   POST /api/upload/video（multipart，带进度/超时）│
  │        │                                      │
  │        └──→ file_id ──────────────────────────┤
  │                                               ▼
  │                            POST /api/analyses/start {file_id, date, kind, mode, hit_time, cuts}
  │                                               │
  │                                               ▼
  │                            建 Analysis 占位 → bind(analysis) → 后台管线
  │                                               │
  └───────────────────────────────────────────────▼→ analysis_id → 订阅状态 → 跳报告页
```

### 4.2 端点契约

#### `POST /api/upload/check`（改造）

请求：`{md5, size_bytes, category?}`（`category` 可选：`video` / `gear_image` / `avatar`，不传行为不变）

| 场景 | 响应 |
|---|---|
| 未命中（无记录 / 物理文件缺失 / size 不一致） | `{hit: false}` |
| 命中 + `security_checked=1` | `{hit: true, safe: true, url, file_id}` |
| 命中 + `security_checked=0` | `{hit: true, safe: false, file_id}` |

- `size_bytes > 0` 时参与一致性校验（取不到 size 时不校验，避免误判 miss）
- **不再以 `ref_count > 0` 为有效条件**（138 后 `ref_count` 语义为业务引用次数）

#### `POST /api/upload/video`（新增）

- 入参：`file`（multipart）+ 视频扩展名白名单（复用 `routers/video.py` 的 `_ALLOWED_VIDEO_EXT`，兼容 `content_type` 以 `video/` 开头）
- 处理：`record, reused = file_service.register(db, user_id, content=..., category="video", original_name=..., ext=...)` → `file_service.mark_security_checked(db, user_id, record.rel_path, True)`（上传阶段职责）
- 鉴权：`Depends(get_current_user)` + `@audit(action="UPLOAD", resource_type="upload")`
- 响应：`{url: record.rel_path, file_id: record.id, mirage: reused}`

#### `POST /api/analyses/start`（改造为 JSON）

- 入参：新增 `AnalysisStartRequest` → `{file_id, date, kind, mode, hit_time, cuts}`；移除 `file: UploadFile` 与 `_save_uploaded_file`
- 校验：`record = file_service.find_by_id(db, user_id, file_id)`，需满足记录存在、`upload_source == "video"`、`file_service.exists(record.rel_path)`；否则 404 + 明确信息，前端降级/提示
- 流程（**与现状完全一致**）：`video_path = file_service.abs_of(record.rel_path)` → 建 Analysis 占位 → `file_service.bind(db, user_id, record.rel_path, "analysis", analysis_id, field="source")` → BackgroundTasks 启动 `_run_analysis_pipeline`
- 响应：`{id: analysis_id, status, pipeline_status, file_id}`

### 4.3 门面新增（`file_service`）

| API | 说明 |
|---|---|
| `find_by_id(db, user_id, file_id)` | 按 `id + user_id + deleted_at is None` 查询，供 `/analyses/start` 校验归属（新增） |
| `find_by_md5(db, user_id, md5, category=None)` | 增加可选 `category` 参数，不传行为不变 |

新增能力须在 `file_store.py` / `file_service.py` 实现并经门面暴露，补 `tests/test_file_facade_api.py` 用例。

### 4.4 前端流程（`analyze.vue`）

1. `chooseMedia` 成功后**立即异步**预计算指纹并缓存（与用户剪辑、设置击球点并行，不在关键路径）
2. 点击「开始分析」：`checkFile(md5, size, "video")` → 命中且 `safe` 取 `file_id`
3. 未命中 / `safe=false` / 预检异常 / MD5 超时（10s）/ 超大文件（>200MB） → `uploadRaw({path:"/upload/video", filePath, timeout})` 取 `file_id`
4. 统一 `post("/analyses/start", {file_id, date, kind, mode, hit_time, cuts})` → 订阅状态 → 跳报告

**加固四项**

| 项 | 实现 |
|---|---|
| 超时 | `resolveUploadTimeout(size) = clamp(size/MB × 3s, 120s, 300s)`；`miniapp/src/manifest.json` 的 mp-weixin 配 `networkTimeout.uploadFile` |
| 进度 | 传 `onProgress`（`uploadRaw` 已支持）显示百分比与已传/总量 |
| 弱网提示 | 上传前 `uni.getNetworkType()`，非 Wi-Fi 且大文件提示，并记入埋点 |
| 重试 | 失败保留 `videoPath` 提供重试入口；重传仍先走预检 |

**埋点**：MD5 计算成功/失败与耗时、命中/未命中、上传进度与失败、弱网/离线、取消（复用页面已有 `createTraceId / logInfo / logError`，统一 `trace_id` 串联）。

### 4.5 上传/分析全程进度体验（决策 10~13）

> 后端无需新增能力：`status` / `pipeline_status` 由 119 的后台管线与 `/analyses/{id}/status` 提供，
> 本次改动全部落在小程序端。

#### 4.5.1 阶段状态机（`analyze.vue`）

```
analysisStage = ""      空闲，不展示遮罩、不阻断交互
      │ 点「开始分析」（先 pause + 隐藏原生 video）
      ▼
analysisStage = "upload"   ① 文件校验 → ② 秒传预检 → ③ 整体上传（/upload/video）
      │ 拿到 file_id 且未被取消
      ▼
analysisStage = "analyze"  ④ /analyses/start（JSON）→ ⑤ 订阅管线进度
      │ completed → 跳报告页；异常/取消 → 静默或 toast 后收尾
      ▼
resetProgressState()  统一清理：analyzing / stage / task / 进度字节 / 文案 / 订阅
```

#### 4.5.2 模态遮罩

| 项 | 实现 |
|---|---|
| 结构 | `.progress-mask`（`position: fixed; inset: 0; z-index: 1000`，半透明黑 0.55）内居中 `.progress-card` |
| 内容 | 旋转指示器 → 阶段标题（`正在上传视频` / `AI 分析进行中`）→ 大号百分比 → 进度条 → 步骤/副文案 → 取消按钮或「分析约需 30~60 秒，请勿退出页面」 |
| 阻断 | `@touchmove.stop.prevent`（编译产物为 `catchtouchmove`）防滚动穿透；`@tap.stop` 使点击遮罩不关闭 |
| 原生组件层级 | `<video>` 为原生组件（层级最高会盖住遮罩）→ 进入模态前 `videoCtx.pause()` + `:class="{ 'video-el--hidden': analyzing }"`（`display:none`）隐藏，退出模态自动复原 |
| 百分比取值 | `analysisStage === "upload"` 取 `uploadPercent`（`onProgress` 实时值）；否则取 `pipelineProgress`（订阅回调值），统一 `clamp(0,100)` |
| 副文案 | 上传阶段 `已传 x.xMB / y.yMB`（`uploadSent` / `uploadTotal`）；分析阶段 `stepLabel(step)` 中文步骤 |

#### 4.5.3 取消与重试

| 场景 | 行为 | 可否重试 |
|---|---|---|
| 上传中（`UploadTask` 已创建） | `task.abort()`，埋点 `video_upload_canceled`，toast「已取消上传」，静默收尾不弹失败文案 | ✅ 直接点「开始分析」，指纹已缓存，再走秒传预检 |
| 预检/算指纹阶段（无 task 可 abort） | 置 `uploadCanceled` + 按钮变「取消中…」；① `onTask` 回调里若已取消立即 `abort()`（不白耗流量）② 拿到 `file_id` 后增设**取消检查点**，被取消则不再调用 `/analyses/start` | ✅ 同上 |
| 个别基础库 `abort()` 不回调 | 取消后 1.5s 兜底调用 `resetProgressState()`，避免模态卡死 | ✅ |
| 分析阶段（已启动后台管线） | **不提供取消入口**：会产生孤儿 Analysis 记录且后台管线不可中断；可退出页面，后台继续跑 | — 列表显示「分析中」，再进该条看实时进度（§4.5.4） |

> 支持取消依赖 `uploadRaw` 透出任务句柄：`UploadOptions` 新增可选 `onTask?: (task: UniApp.UploadTask) => void`，`uni.uploadFile` 返回后同步回调。

#### 4.5.4 `processing` 态贯穿列表与报告页

| 位置 | 实现 |
|---|---|
| 列表 `coach.vue` | `status === "processing"` → 封面角标 `⏳`、摘要「分析进行中…」（青柠色）、右侧转圈 + 「分析中」（替代原「本地」文案）；存在 processing 项时启动 **4s 轮询 `getAnalyses`**，全部完成后自动停止，`onHide` / `onUnmounted` 清理定时器（轮询失败静默，下周期重试） |
| 报告页 `report.vue` | `isProcessing` 时渲染独立进度块（转圈 + 百分比 + 进度条 + `stepLabel` + 「可先返回列表，稍后回来查看」），**不渲染空报告**；进入即 `createStatusSubscriber(id)`：`completed` → `getAnalysis(id)` 重载并自动渲染完整报告，`failed` → 切失败 banner 并显示 `pipeline_status.error`；`onUnload` 停止订阅 |
| 副作用规避 | 进行中时不进入 `report-body` 分支 → 删除按钮自然隐藏，避免删除与后台写库竞态 |
| 步骤文案 | `services/analysisStatus.ts` 导出 `stepLabel(step)`（`init/upload/ai/pose/finalize` → 中文，未知回退「分析中…」），`analyze.vue` 与 `report.vue` 共用 |

## 八、风险与注意事项

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| `/upload/video` 整文件读入内存 | 大视频内存峰值高 | 与现状 `/analyses/start` 一致；阶段二分片上传根治 |
| 客户端 MD5 与服务端不一致 | 误判 miss，退化为正常上传 | 视频不压缩、原样上传，两端均为全文件 MD5；仅影响秒传命中率，不影响正确性 |
| `file_id` 越权 | 跨用户复用文件 | 门面 `find_by_id` 强制带 `user_id` 条件，不从客户端接受路径 |
| 改造 `/analyses/start` 签名 | 旧调用方失效 | 已核实无测试与其它调用方直接依赖；小程序端同步改造 |
| 视频无微信安全检查 | 违规内容无法被官方接口拦截 | 官方三件套不支持视频、平台不要求；场景为本人可见 + 分享合成图，如需增强另开方案（ffmpeg 抽帧 + imgSecCheck） |
| MD5 计算耗时 | 低端机大文件卡顿 | 选后异步预计算 + 10s 超时 / >200MB 跳过，静默退回上传 |
| 阶段二临时分片残留 | 磁盘占用 | complete 时清理，并纳入既有清理任务 |
| 列表 4s 轮询 | 有 processing 记录时增加后台请求量 | 仅在该 user 列表存在 processing 项时启动，全部完成后立即停止；`onHide`/`onUnmounted` 清理定时器；轮询失败静默 |
| `<video>` 原生组件层级最高 | 遮罩被视频盖住 | 分析开始前 `pause()` + `display:none`；退出模态后自动复原播放按钮状态 |
| `abort()` 个别基础库不回调 | 模态卡死无法退出 | 取消后置 1.5s 兜底 `resetProgressState()`；收尾统一走单一函数避免状态残留 |
| 分析阶段允许取消 | 孤儿 Analysis 记录 / 后台管线无法中断 | 当前不提供取消入口；退出页面不影响后台执行。如后续需真取消，后端须新增取消端点（管线读取消标记 + 记录置 failed），届时另开方案 |
