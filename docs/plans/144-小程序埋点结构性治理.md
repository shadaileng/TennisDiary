# 小程序埋点结构性治理

## 一、背景与问题

Plan 143 完成了 `analyze.vue` 的事件链路重构与上下文丰富化。全量审查其余 15 个事件日志文件（~90 个事件），发现以下结构性问题：

### 1.1 Action 名称冲突

| 冲突 action | 涉及文件 | 影响 |
|---|---|---|
| `offline_create_pending` | diary.ts、gear.ts、weight.ts | Admin 按 action 查询无法区分来源 |
| `offline_sync_failed` | mine.vue、sync.ts | 同名不同源，日志关联歧义 |

### 1.2 缺失 traceId（~12 个事件）

| 文件 | 事件 | 严重程度 |
|---|---|---|
| profile-edit.vue | 隐私授权 4 事件（`privacy_nickname_request/agree/denied/error`） | 高 |
| request.ts | 网络层 4 事件（`api_error`/`http_error`/`network_error`/warn） | 中 |
| report.vue | `report_reload_failed` | 低 |
| App.vue | 全局崩溃 4 事件 | 低（可接受） |

### 1.3 空 params（~15 个 start 事件）

| 文件 | 事件 | 缺失上下文 |
|---|---|---|
| auth.ts | `login_start` | 无 login method、platform |
| share.vue | `share_load_diaries_start`、`share_load_analyses_start` | 空 |
| gear/form.vue | `gear_photo_choose`、`gear_photo_guest_checked`、`gear_photo_offline_local`、`gear_photo_selected` | 无 guest 标记、网络状态 |
| profile-edit.vue | `avatar_update_start`、`avatar_upload_start`、`profile_save_avatar_start` | 空 |
| mine.vue | `mine_stats_load` | 空 |
| stats.vue | `stats_load` | 空 |

### 1.4 无 EV 常量

仅 `analyze.vue` 定义了 `EV` 常量对象，其余 15 个文件全部使用字符串字面量，存在拼写风险和重构困难。

## 二、目标

1. **消解 action 名称冲突**：2 处冲突 action 重命名，加模块前缀区分来源
2. **补全缺失 traceId**：高/中优先级的 8 个事件补上 traceId
3. **丰富空 params**：15 个 start 事件补充有价值的客户端上下文
4. **建立共享 EV 常量**：创建 `eventLogger.ts` 共享常量文件，消除字符串字面量

**不改动**：
- 不改动 `analyze.vue`（已由 Plan 143 完成）
- 不改动 App.vue 全局崩溃事件（崩溃级可接受无 traceId）
- 不改动事件上报协议（由 Plan 142 处理 params 重构）
- 不新增页面访问 PV 埋点

## 三、设计原则

### 3.1 命名规范

- Action 命名：`{模块}_{动作}` snake_case（如 `diary_create`、`gear_photo_choose`）
- 消歧时加模块前缀：`diary_offline_create_pending` 替代 `offline_create_pending`
- 与 Plan 143 的 `analyze.vue` EV 常量命名风格保持一致

### 3.2 traceId 链路规则

- 同一用户操作链路内所有事件共享 traceId
- 请求拦截器层（request.ts）事件：接收 caller 传入的 traceId（通过 extra 透传），无法获取时 fallback 内联 createTraceId
- 隐私授权流程：在流程入口 createTraceId，全程传递

### 3.3 params 丰富原则

- Start 事件：记录「操作对象 + 客户端环境」（如 guest 标记、网络类型、文件大小）
- Success 事件：记录「结果标识 + 耗时」（如 ID、duration_ms）
- Failed 事件：记录「输入参数 + 错误信息」（保持现有模式）

### 4.3 traceId 补全

#### 4.3.1 profile-edit.vue — 隐私授权流程（4 事件）

```ts
// 在 handleChooseNickname 或隐私流程入口处
const privacyTraceId = createTraceId()

// 原：无 traceId
logInfo("privacy_nickname_request", {...}, undefined, "privacy_nickname_request")
// 改：传入 privacyTraceId
logInfo("privacy_nickname_request", {...}, undefined, EV.PRIVACY_NICKNAME_REQUEST, privacyTraceId)
```

4 个事件统一传入 `privacyTraceId`，在流程入口创建，流程结束后不再使用。

#### 4.3.2 request.ts — 网络层事件（4 事件）

request.ts 的拦截器函数签名改为接受可选 traceId：

```ts
// 原函数签名
function handleApiError(res, options) { ... }

// 改为
function handleApiError(res, options, traceId?: string) { ... }
```

各调用点（`logError`/`logWarn`）传入 traceId：

| 事件 | 改动 |
|------|------|
| `api_error` | 传入 traceId |
| warn (无 action) | 补 action 名 `api_error`，传入 traceId |
| `http_error` | 传入 traceId |
| `network_error` | 传入 traceId |

> 注：request.ts 的 traceId 来源是调用方通过 `extra` 传入。需要在 request 拦截器中从 extra 提取 traceId 并传递给 error handler。如果调用方未传，则 fallback `createTraceId()`。

#### 4.3.3 report.vue — report_reload_failed

```ts
// 原：无 traceId
logError("report_reload_failed", {...})
// 改：传入 loadTraceId（复用 report_load 链路的 traceId）
logError("report_reload_failed", {...}, undefined, EV.REPORT_RELOAD_FAILED, loadTraceId)
```

需要在 report.vue 顶部声明 `loadTraceId` 并在 load 链路中共享。
