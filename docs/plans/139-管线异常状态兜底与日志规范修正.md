### 2.6 前端订阅泄漏：`onUnmounted` ≠ `onUnload`（G6）

## 三、loguru 日志规范（本项目强制）

### 3.1 结论与实测

loguru 使用 `str.format()` 语义，即 **`{}` 风格**；`%s`（printf 风格）**不是** loguru 的格式化语法，传入的位置参数会被**静默丢弃**，只留下原始占位符。

实测（项目环境实跑）：

```python
logger.warning('printf风格: %s - %s', 'ARG1', 'ARG2')
logger.warning('braces风格: {} - {}', 'ARG1', 'ARG2')
```
```
WARNING | printf风格: %s - %s      ← 参数被丢弃，输出原始占位符
WARNING | braces风格: ARG1 - ARG2  ← 正常替换
```

项目内交叉印证：

| 位置 | 风格 | 实际输出 |
|---|---|---|
| `file_service.py:396` `{}` | ✅ | `user.log:2903` → `登记新文件: md5=c7749e27ed33 rel_path=videos/2/… file_id=592` |
| `pipeline.py:317` `%s` | ❌ | `app.log:7203` → `抽帧登记失败(非致命): %s - %s` |

> 官方文档同步说明：传参即触发 `str.format()`，若消息含 `{}` 会抛 `KeyError` / `ValueError` / `IndexError`——这正是 `AGENTS.md` 禁止 `f"...{exc}"` 的由来。

### 3.2 规范表

| 场景 | 正确写法 | 说明 |
|---|---|---|
| 普通变量 | `log.info("登记完成: {} 条", n)` | `{}` 是唯一可靠风格 |
| 异常（不带堆栈） | `log.error("登记失败: {}", exc)` | 直接传异常对象 |
| 异常（带堆栈） | `log.exception("管线失败: {}", exc)` | 或 `log.opt(exception=True).error("…", exc)` |
| 仅记异常类型 | `log.error(f"失败: {type(exc).__name__}")` | f-string **不额外传参**时安全 |
| ❌ 禁止 | `log.error("失败: %s", exc)` | **参数静默丢失**，日志只剩 `失败: %s` |
| ❌ 禁止 | `log.error(f"失败: {exc}", extra=1)` | 异常 `str()` 含 `{}` → 二次 format 抛 `KeyError` |

### 3.3 必须修正的规范条款

`AGENTS.md` 核心约束第 5 条现有建议 **本身无效**，需改写：

```diff
- 应写 `log.error(f"处理失败: {type(exc).__name__}")` 或 `log.error("处理失败: %s", exc)`。
+ 应写 `log.error(f"处理失败: {type(exc).__name__}")` 或 `log.error("处理失败: {}", exc)`（loguru 用 `{}`，
+ 严禁 `%s` 风格——参数会被静默丢弃）；需堆栈时用 `log.exception("处理失败: {}", exc)`。
```

## 四、关键决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | 日志风格统一为 `{}`，`%s` 全量清除 | loguru 语义，`%s` 必然失效（§3 实测） |
| 2 | `register_batch` 的 `flush()` 补 `try/except → rollback()` | 与单文件 `register`（296-305 行）保持一致，杜绝污染外层连接 |
| 3 | 管线 except **先 `rollback()` 当前连接再写 `failed`** | 连接是自己弄坏的，先修复再写；恢复后原连接即可用 |
| 4 | 再叠加**独立新连接兜底**写 `failed` | 双保险：即便 `rollback` 也失败，仍能落状态 |
| 5 | 兜底写入自身用 `try/except` 包裹，失败只记日志 | 保证 `run_pipeline` 始终返回，不因兜底失败二次抛出 |
| 6 | 增加孤儿 `processing` 超时清理 | 终结历史遗留与未来极端情况，前端不再无限轮询 |
| 7 | ~~本次不动小程序端~~（**v1.2.0 起已作废**） | v1.2.0 起因发现订阅泄漏与列表无限轮询，小程序端已纳入改动，见决策 11-14 |
| **8** | **步骤异常 fail-fast：致命步骤不 catch，直接终止管线** | 现有 `# 登记失败非致命` 是错误定性——没有帧，AI/pose 就失去输入，继续跑只会产出垃圾报告（§2.5 路径 A） |
| **9** | **`_finalize` 发现 `video_url` 为空时置 `failed`**，不再 warn 保留孤儿 | 该分支是**独立的** processing 孤儿来源，仅修连接问题无法消除（§2.5 路径 B） |
| **10** | **可降级步骤写入 `pipeline_status.degraded` 标记** | 保留"部分功能降级仍完成"的能力，但必须可观测，不允许无痕降级 |
| **11** | **小程序页面清理一律用 `onUnload`，禁用 `onUnmounted` 承担页面级清理** | `onUnmounted` 是 Vue 组件生命周期，小程序页面销毁（navigateBack/回收）不保证触发（§2.6） |
| **12** | **`analyze.vue` 只用 `onUnload`，不加 `onHide` 停止订阅** | 该订阅绑定在 `startAnalysis` 的 Promise 上，页面隐藏即停会导致 Promise 永不 resolve；只在真正卸载时停才符合语义 |
| **13** | **`PollingSubscriber` 增加最大轮询时长/次数上限，超时自停** | 防御后端长期卡 `processing` 时前端无限打请求 |
| **14** | **列表页取消自动轮询，改为用户主动下拉刷新** | 自动轮询把"processing 是短暂状态"当前提，后端卡住即无限请求（§6.3）；改下拉刷新后更新时机由用户掌控，且 `onShow` 返回列表仍自动刷一次保证时效 |

## 五、后端修复设计（状态兜底 + fail-fast）

### 5.1 管线异常收尾流程（目标态）

```python
# pipeline.py run_pipeline
except Exception as e:
    # 1) 真实异常落盘（{} 风格 + 堆栈）
    log.exception("管线失败 analysis_id={} error={}", self.analysis_id, e)

    # 2) 先修复自身连接，再写失败态
    try:
        self.db.rollback()
        self._update_step_status(PipelineStep.FINALIZE, StepStatus.FAILED, error=str(e))
        self._update_analysis_field(status="failed")
    except Exception as recover_exc:
        # 3) 独立新连接兜底：不受 self.db 状态影响
        log.error("管线失败态写入失败，启用独立连接兜底: {}", recover_exc)
        _force_fail(self.analysis_id, str(e))

    return {"status": "failed", "error": str(e)}
```

`_force_fail` 独立实现（新 `SessionLocal`，写完立即关闭）：

```python
def _force_fail(analysis_id: int, error: str) -> None:
    """独立连接兜底置 failed：不依赖管线可能已损坏的 self.db"""
    from app.core.database import SessionLocal
    db = SessionLocal()
    try:
        db.execute(
            sa_update(Analysis)
            .where(Analysis.id == analysis_id)
            .values(status="failed")
        )
        db.commit()
    except Exception as exc:                      # 兜底自身也不允许抛出
        log.error("独立连接兜底置 failed 仍失败: {}", exc)
    finally:
        db.close()
```

## 六、前端修复设计（订阅生命周期 + 下拉刷新）

> 本章对应目标 G6「离开即停」。后端改动见 §五。

### 6.1 订阅生命周期规范（G6）

| 规则 | 说明 |
|---|---|
| 页面级清理用 **`onUnload`** | 小程序页面销毁的唯一可靠钩子；`onUnmounted` 仅用于**组件**内部清理 |
| 绑定 Promise 的订阅**不加 `onHide` 停止** | `analyze.vue` 场景：隐藏即停会使 Promise 永不 resolve |
| 纯展示型轮询用 `onHide` / `onShow` 停启 | 若后续新增列表类轮询，隐藏时停、显示时恢复（原 `coach.vue` 列表轮询已由 Step 7 改为下拉刷新，不再适用） |
| 订阅器自身加**上限保护** | 最长时长/最大次数，超时自停并回调 |

### 6.2 关键改造点

**（1）`analyze.vue`（必须）**

```ts
import { onUnload } from "@dcloudio/uni-app";

// 页面卸载时清理（小程序页面须用 onUnload，onUnmounted 不保证触发）
onUnload(() => {
  stopStatusSubscriber();
});
```

> 保持**只**用 `onUnload`：该订阅服务于 `startAnalysis` 的 Promise，若额外在 `onHide` 停止，
> 则用户进入下一页再返回时 Promise 永远无法 resolve（决策 12）。

**（2）`coach.vue` —— 无需处理（已被 Step 7 覆盖）**

原 `onUnmounted(stopPolling)` / `onHide(stopPolling)` 随列表轮询一并移除（§6.3），
该文件已不再持有任何定时器，**不存在生命周期泄漏问题**。

**（3）`analysisStatus.ts` 订阅器上限保护（决策 13）**

```ts
// 注意：analysisStatus.ts 当前无 logger，需引入（与页面层一致，用 @/utils/eventLogger）
import { logWarn } from "@/utils/eventLogger";

class PollingSubscriber {
  private maxDurationMs = 5 * 60 * 1000;      // 最长 5 分钟
  private startedAt = 0;

  /** 超时回调：通知页面提示用户，避免"一直转圈但已无请求" */
  constructor(
    analysisId: number,
    callback: StatusCallback,
    pollInterval = 2000,
    private onTimeout?: () => void,
  ) { /* ... */ }

  start() {
    this.startedAt = Date.now();
    this.fetchStatus();
    this.timer = setInterval(() => {
      if (Date.now() - this.startedAt > this.maxDurationMs) {
        logWarn("状态轮询超时，已停止", { analysis_id: this.analysisId });
        this.stop();
        this.onTimeout?.();                   // ← 关键：必须通知 UI，不能静默停止
        return;
      }
      this.fetchStatus();
    }, this.pollInterval);
  }
}
```

> **与 §5.3 的阈值关系**：前端轮询上限 5 分钟 < 后端孤儿清理 10 分钟。
> 中间 5 分钟用户若停留在报告页会看到"进行中"但已无请求 —— 因此 **`onTimeout` 必须回调给 UI 提示**
> （如"分析超时，请下拉刷新或稍后重试"），不能静默停止。

### 6.3 列表页改下拉刷新（决策 14，**已实施**）

#### 动机

`coach.vue` 原实现：列表中存在 `processing` 记录即启动 4s `setInterval` 轮询 `GET /api/analyses`，
**唯一停止条件是"后端让记录离开 processing"**。

```js
// 改动前
if (hasProcessing.value) startPolling();     // 4s 轮询
if (!hasProcessing.value) stopPolling();     // 仅当无 processing 才停
```

这把"processing 是**短暂**状态"当成前提。`id=16` 永久卡 processing → `hasProcessing` 恒为 `true`
→ 只要停留在列表页就无限每 4s 打一次请求（对应 §1.2 日志中的 `GET /api/analyses`）。

#### 目标态：用户主动触发

| 时机 | 行为 |
|---|---|
| 进入 / 返回列表页（`onShow`） | 自动加载一次，保证从报告页返回时看到最新状态 |
| **用户下拉**（`onPullDownRefresh`） | 主动刷新列表 |
| 其他 | **不发起任何请求** |

不再依赖后端状态变化来停止，从根上消除"后端卡住 → 前端无限请求"。

#### 实现

**`pages.json`**（启用页面下拉刷新）：

```json
{
  "path": "pages/coach/coach",
  "style": {
    "navigationBarTitleText": "电子教练",
    "enablePullDownRefresh": true
  }
}
```

**`coach.vue`**：

```ts
import { ref } from "vue";
import { onPullDownRefresh, onShow } from "@dcloudio/uni-app";

onShow(async () => {
  await loadAnalyses();
});

/** 下拉刷新：由用户主动触发更新（替代自动轮询，避免 processing 卡住时无限请求） */

    await loadAnalyses();
  } finally {
    uni.stopPullDownRefresh();
  }
});
```

> 移除项：`POLL_INTERVAL_MS`、`pollTimer`、`hasProcessing`、`startPolling`、`stopPolling`，
> 以及 `computed` / `onHide` / `onUnmounted` 的相关导入。
> `uni.stopPullDownRefresh()` 置于 `finally`，保证加载失败也能收起下拉动画。

## 十、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 全量改 `%s` 范围大、易漏 | 仍有失效日志 | 用 `grep -rn '"[^"]*%s"' server/app` 全量扫描；加测试断言日志输出不含 `%s` |
| `rollback()` 误伤正常事务 | 丢失已 flush 的写入 | 仅在 `except` 分支调用；`register_batch` 的 rollback 紧随 `flush()` 失败，无已提交数据 |
| 独立连接兜底与主线程并发写 | SQLite 锁 | 兜底写入极短（单条 UPDATE + commit）；`timeout=30` 已配 |
| 超时清理误杀长任务 | 正常分析被置失败 | 阈值默认 10 分钟并做成配置项；仅清理 `created_at` 超时的记录 |
| 兜底写入自身失败 | 状态仍卡 processing | 兜底再包 `try/except`，失败只记日志；配合 §5.3 超时清理最终兜底 |
| 修改 `AGENTS.md` 规范 | 与既有习惯冲突 | 同步在 §3 给出实测证据，避免再次回退到 `%s` |
| **fail-fast 提高失败率** | 原本"带病完成"的分析现在会明确失败，失败数短期上升 | 这是**正确性修正**而非回归：带空输入的报告本就不可用；上线前确认无测试依赖旧静默行为（Step 5 已标注） |
| 致命/可降级划分过严 | 可用结果被判失败 | 仅把"无输入即无意义"的环节判致命（抽帧、播放短片、video_url）；骨架/清理类保持可降级并打标 |
| `_finalize` 置 failed 后用户无法重试 | 体验下降 | 前端保留 `videoPath` 可直接重新分析（137 已实现取消/重试）；错误文案明确"播放短片缺失，请重新分析" |
| **`analyze.vue` 误加 `onHide` 停止订阅** | `startAnalysis` 的 Promise 永不 resolve，分析卡死 | 严格遵守决策 12：该订阅**只**用 `onUnload`；代码注释说明原因，避免后续误改 |
| **轮询上限误杀正常长任务** | 正常分析被前端提前停轮询 | 上限默认 5 分钟（管线实际 30~60s），且仅停止轮询、不影响后端；用户重新进入页面会重新订阅 |
| **轮询超时后 UI 无感知** | 前端已停请求但页面仍显示"进行中"，用户困惑 | 超时**必须**通过 `onTimeout` 回调通知 UI 提示（§6.2(3)），禁止静默停止 |
| **前后端超时阈值不一致** | 前端 5min 停轮询、后端 10min 才置 failed，中间 5min 状态不更新 | 前端超时即提示用户主动刷新；后端阈值独立兜底；两者无需强一致，但 UI 提示必须到位 |
| 其他页面存在同类 `onUnmounted` 误用 | 泄漏未根除 | 全量扫描 `onUnmounted`，页面组件一律改 `onUnload`；真正的子组件才保留 `onUnmounted` |
| **改下拉刷新后状态更新不及时** | 用户看不到分析已完成 | `onShow` 仍自动加载一次；processing 记录保留 ⏳ 与"分析中"标识，用户下拉即可刷新；报告页订阅（Step 9 后为 `onUnload`）提供实时进度 |
| 下拉刷新与 `onShow` 重复请求 | 进入页面即下拉会打两次 | 请求轻量且幂等，可接受；若需优化可在 `loadAnalyses` 加进行中去重 |
