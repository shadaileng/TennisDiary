# Step 111：文件使用标记（基于数据库引用核查）

## 一、目标

在现有 `File` 表 `ref_count` + `deleted_at` 基础上，新增**明确的「使用中 / 可清除」语义标记**，通过**实时核查业务表引用**计算，不引入新 DB 列（避免脏数据），并在后端 API 与管理端双向暴露。

核心问题：
1. 管理端当前只显示 `ref_count`，没有明确的使用状态标记；
2. `ref_count` 可能因业务删除时漏调 `decrement_ref_count` 而虚高——记录显示在用，实际业务已不引用；
3. 磁盘孤儿文件（未在 File 表注册）完全无状态标注。

目标效果：
- 管理端文件列表每行展示「使用中」或「可清除」彩色徽章，hover 显示原因；
- 统计卡片增加「可清除」计数；
- 扫描弹窗中的孤儿文件标注为「可清除·孤儿」；
- 可选按使用状态过滤。

## 二、状态定义

新增 `usage_status` 字段，取值与含义：

| 值 | 中文标签 | 判定条件 | 是否可安全清理 |
|----|---------|---------|:---:|
| `in_use` | 使用中 | 业务记录存在且仍引用该文件 | ✗ |
| `unreferenced` | 可清除（引用失效） | File 记录存在，但引用的业务记录不存在或不再引用 | ✓ |
| `marked_deleted` | 可清除（已软删） | `deleted_at` 非空，等待物理清理 | ✓ |
| `orphan` | 可清除（磁盘孤儿） | 文件在磁盘存在，但 File 表无记录 | ✓ |

`usage_reason` 提供具体原因字符串，用于 hover 提示，例如：
- `"引用计数已归零"`
- `"用户头像引用已失效"`
- `"装备记录已被删除"`
- `"分析报告记录不存在"`
- `"已标记删除，待物理清理"`
- `"磁盘孤儿，未注册到文件表"`

## 三、核查规则（`classify_file_usage`）

新建服务函数 `file_service.classify_file_usage(db, file_record: File) -> tuple[str, str]`，按优先级顺序判定。所有匹配均为**精确路径比对**（业务表存的就是与 File.rel_path 同源的字符串）。

1. **已软删**：`file_record.deleted_at is not None` → `("marked_deleted", "已标记删除，待物理清理")`
2. **引用归零**：`file_record.ref_count <= 0` → `("unreferenced", "引用计数已归零")`
3. **有 business_type + business_id**：按业务类型查对应业务表做路径匹配
   - `user`：查 `User(id == business_id)`；若存在且 `avatar_url == rel_path` → `("in_use", "用户头像引用有效")`；否则 → `("unreferenced", "用户头像引用已失效")`
   - `gear`：查 `Gear(id == business_id)`；若存在且 `photo == rel_path` → `("in_use", "装备图片引用有效")`；否则 → `("unreferenced", "装备记录引用已失效")`
     - > **说明**：凡是有 `business_type=gear` 的 `File` 记录，当初必由 `/api/upload/gear-image` 生成，其 `photo` 字段即为 `rel_path`（不会是 dataURL）。若业务表 `photo` 与 `File.rel_path` 不一致，说明该 gear 已换图，原文件确实不再被引用 → 标「可清除」是正确的。无需额外保守处理。
   - `analysis`：查 `Analysis(id == business_id)`；若存在且 `(video_url or thumb or highlights or pose)` 任一含 `rel_path` → `("in_use", "分析报告引用有效")`；否则 → `("unreferenced", "分析报告引用已失效")`
   - 未知 `business_type` 且 `business_id is not None`：无法验证 → `("unreferenced", f"未知业务类型 {business_type}")`（保守不猜）
4. **无 business_id（upload_source 推断兜底）**：通过 `upload_source` 字段推断应查哪个业务表
   - `avatar`：查 `User.avatar_url == rel_path AND User.id == file.user_id` → 匹配 `("in_use", "用户头像引用有效")`；否则 `("unreferenced", "用户头像引用已失效")`
   - `gear_image`：查 `Gear.photo == rel_path AND Gear.user_id == file.user_id` → 匹配 `("in_use", "装备图片引用有效")`；否则 `("unreferenced", "装备记录引用已失效")`
   - `video` / `video_frame` / `skeleton`：查 `Analysis` 中 `(video_url or thumb or highlights or pose)` 任一含 `rel_path` AND `analysis.user_id == file.user_id` → 匹配 `("in_use", "分析报告引用有效")`；否则 `("unreferenced", "分析报告引用已失效")`
   - 其他未知 upload_source：`("unreferenced", "未绑定业务记录")`

> **路径一致性验证**：业务表存储路径与 `File.rel_path` 同源，均通过 `file_service.make_rel_path(dir, user_id, filename)` 生成（`{dir}/{user_id}/{uuid}.{ext}`）。各上传端点（`upload_avatar`、`upload_gear_image`、`video/upload`）与落库流程（`register_ai_files`）都用同一返回值，确保精确匹配有效。

> **设计说明**：不依赖 File 表的 `business_type`/`business_id` 作为唯一依据——这两个字段只在 `register_ai_files`（analysis 落库时）写入，avatar/gear/video 上传时均为 NULL。通过 `upload_source` 推断兜底，确保所有上传渠道的文件都能正确分类。

## 六、注意事项

1. **无数据库迁移**：所有状态实时计算，不新增列，无需 Alembic 迁移。
2. **标记范围仅限 File 表已有行**：`usage_status` 仅对已进入 `File` 表的记录计算。未注册的磁盘孤儿通过「扫描」功能单独处理（已用 `orphan` 状态标注），两者互不干扰；不是「未覆盖的异常」，是「不在本功能的标记对象内」。
3. **性能**：每文件一次 classify 查询（≤3 条 SELECT），admin 分页 ≤100 行 → 最多 300 条查询。对本地 SQLite 可接受；若后续数据量大，可优化为批量查询 + 内存 map。
4. **一致性**：业务表写入/删除时不缓存 usage_status，每次列表刷新即重算，保证数据一致。
5. **AGENTS.md 规则 4（共享响应模型变更）**：`AdminFileResponse` 已在 `app/schemas/admin_file.py` 中全量使用（grep 确认只有 `admin/files.py::_file_to_response` 一处构造，无 model_validate 散点）；新增字段只需改一处。`OrphanFileInfo` 同理，只在 `scan_orphan_files` 结果映射处。
6. **异常日志风格**：`file_service.py` 新增代码需遵循 AGENTS.md §6.1：禁止 `f"...{exc}"`，使用 `%s` 风格。
7. **路径匹配假设已验证**：各上传端点（`upload_avatar`、`upload_gear_image`、`video/upload`）返回的 `url` 即为 `File.rel_path`，客户端回写业务表时原样存储；`register_ai_files` 亦用同一批 rel_path 注册。精确路径比对可靠。
8. **upload_source 推断兜底**：`get_or_create_file` 不写 `business_type`/`business_id`（仅 `register_ai_files` 写入），因此 avatar/gear/video 等文件需通过 `upload_source` 推断应查哪个业务表。classify 对这三种 source 均做精确路径匹配，匹配成功则判 in_use，否则 unreferenced。
