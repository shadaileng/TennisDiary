# 117：原视频信息表与衍生文件登记

> ⚠️ **本文已归档**：原视频信息表设计已并入 [118：分析流水线重构与视频信息表](./118-分析流水线重构与视频信息表.md)（表更名为 `analysis_video_info`，分析流程重构为「先建 analysis_id 后分步更新」）。新实施以后者为准。

## 一、背景与根因

电子教练上传视频后，当前实现存在三个问题：

1. **原视频被系统删除**：`process_video` 在裁剪拼接后执行 `os.unlink(path)`（`app/services/video_service.py:420-421`），把原始整片删掉。原始整片本是秒传（md5 去重）的基础，也是重新裁剪/重跑 AI 的源，不应被系统自动删除。
2. **播放短片未纳入文件管理**：上传端点只给原始 `video` 和抽帧 `video_frame` 建了 File 记录，而真正被播放的 `working`（裁剪/拼接后的短片，`result["video_url"]` 指向的文件）**没有 File 记录**，因此文件管理列表看不到它、也无法手动管理。
3. **缺少裁剪信息与衍生文件的统一登记**：没有任何数据记录某次分析对应的「原视频是谁、裁剪起止/击球点是什么、产生了哪些衍生文件（短片/帧/骨架/封面）」，也无法关联到 `Analysis` 记录，不利于追溯与文件管理。

### 小程序端实际使用情况（边界条件）

经核查 `miniapp/src/pages/coach/report.vue`：

- 播放标签「原视频」播放的是 `analysis.video_url`，即**裁剪后的 H.264 短片（working）**，并非 HEVC 原始整片；原始 `video` File 记录**从不被小程序引用**。
- 骨架标签播放 `pose.skeleton_video_url`（H.264 骨架视频）。

| 文件 | upload_source | 小程序是否使用 | 手动删除影响 |
|---|---|---|---|
| 原视频整片 | `video` | 否（从不引用，播放用的是衍生短片） | 不影响小程序；失去秒传基础/重裁剪源 |
| 播放短片（裁剪 H.264） | `video_playback` | 是（「原视频」标签 `analysis.video_url`） | 播放标签失效 |
| 骨架视频 | `skeleton` | 是（「骨架视频」标签） | 骨架标签失效 |
| 骨架帧 | `skeleton` | 是（无骨架视频时回退展示） | 回退展示失效 |
| 封面 thumb | `analysis_thumb`/`skeleton` | 是（报告封面 + 历史列表） | 封面/历史缩略图失效 |
| 抽帧帧图 | `video_frame` | 否（仅 AI 评分输入） | 不影响小程序；影响重新 AI 分析 |

**结论**：原始整片与抽帧帧图不被小程序直接消费；播放短片/骨架/封面被消费。手动删除任一 File 仅影响上表对应项。

## 二、目标

1. **原始视频始终保留**，作为秒传基础，系统不自动删除（删除仅由文件管理手动操作）。
2. **衍生文件生成即纳入文件管理**：播放短片（`video_playback`）在上传时即建立 File 记录（当前缺失，需补）。
3. **新建「原视频信息表」**记录：原视频来源（File）、裁剪信息（segments/hit_time/mode/kind）、衍生文件清单（短片/帧/骨架/封面），并关联 `Analysis` 记录。
4. **明确不做**：原视频转码（HEVC 原片保持原样）；历史数据回填；级联删除。
5. **文件管理「使用中」筛选以边界条件为准**：`classify_file_usage` / `bulk_classify_files` 的 in_use 判定必须以「一小程序端实际使用情况（边界条件）」为标准（见第一节边界表），详见 4.6。

## 三、数据模型（新建表，不改 `File`）

`app/models/original_video_info.py` → 表 `original_video_info`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | Integer PK | 自增主键 |
| `user_id` | Integer (index) | 所属用户 |
| `source_file_id` | Integer FK→`files.id` (ondelete SET NULL) | 原视频 File 记录 |
| `playback_file_id` | Integer FK→`files.id` (ondelete SET NULL) | 播放衍生（短片）File 记录，便于回查 |
| `analysis_id` | Integer FK→`analyses.id` (ondelete SET NULL, index) | 关联分析记录 |
| `cut_info` | JSON | 裁剪信息：`{segments, hit_time, mode, kind}` |
| `derivatives` | JSON | 衍生文件清单：`[{kind, rel_path, file_id, mime_type, size_bytes}, ...]` |
| `created_at` | Float | 时间戳 |

- 在 `app/models/__init__.py` 注册 `OriginalVideoInfo`（AGENTS：新模型必须登记）。
- `derivatives` 为去规范化清单：每个衍生文件本身已是 `File` 记录（文件管理），本表只做「登记 + 关联」。

## 四、后端改动

### 4.1 保留原视频 `app/services/video_service.py`

- 删除 `process_video` 中 `os.unlink(path)`（`video_service.py:420-421`），原始整片始终保留。
- **不转码原视频**：有 `cuts` 时 `trim_video`（`video_service.py:205`）已用 `libx264` 产出 H.264 短片；无 `cuts` 时 `working = 原片`（按设计上传必带 cuts，原片保持 HEVC 不转码）。

### 4.2 衍生登记服务 `app/services/file_service.py`

新增两个函数：

- `create_original_video_info(db, user_id, source_file_id, playback_file_id, cut_info, derivatives)` → 建表行，返回行对象。
- `attach_analysis_to_video_info(db, playback_file_id, analysis_id, extra_derivatives)` → 分析落库时回填 `analysis_id` 并把骨架/封面等 `extra_derivatives` 合并进 `derivatives`。

### 4.3 上传端点 `app/routers/video.py`

- 原 `video` File 记录照常创建（秒传基础，不删除）。
- `process_video` 成功后：
  - 为 **working 播放短片** 建 File 记录：`get_or_create_file(upload_source="video_playback", rel_path=working_rel, mime_type="video/mp4", original_name=..., size_bytes=...)`。
  - 抽帧帧图保持现有 `get_or_create_file(upload_source="video_frame", ...)`。
  - 调 `create_original_video_info(source_file_id=原片.id, playback_file_id=短片.id, cut_info={segments, hit_time, mode, kind}, derivatives=[短片信息, 各帧信息])`。
- `result["video_url"]` 仍指向 `working_rel`（不变）。

### 4.4 分析落库 `app/routers/analyses.py`

- `create_analysis` 保留 `register_ai_files`（骨架/封面入文件管理 + 关联 analysis）。
- 新增：调 `attach_analysis_to_video_info(playback_file_id=由 video_url 反查, analysis_id=analysis.id, extra_derivatives=[骨架视频/骨架帧/封面/highlights 的信息])`。
  - 由 `video_url` 反查其 File 记录 → 取 `OriginalVideoInfo.playback_file_id` 定位表行。

### 4.5 删除 `app/routers/admin/files.py`

- `delete_file` **不改**（手动删除单条 File + 软删 + 清理磁盘）。无级联删除。
- 新表外键 `ondelete=SET NULL`：删除原片或衍生 File 后，对应表行外键自动置空，行本身保留为元数据，无害。

### 4.6 文件管理「使用中」筛选对齐边界条件

当前 `classify_file_usage`（`file_service.py:565`）与 `bulk_classify_files`（`:661`）的 in_use 判定是「按 `upload_source` 推断后，拿 `rel_path` 去逐个 Analysis 的 `video_url/thumb/highlights/pose` 做字符串包含匹配」。两个问题需修正，使其以第一节边界表为准：

1. **`video_playback` 未被识别**：4.3 落地的播放短片 `upload_source="video_playback"` 在上传时未设置 `business_type`，而 `:641` 的 `src in ("video","video_frame","skeleton")` 不含它 → 即使正被分析引用，也会落到 `unreferenced / 未绑定业务记录`，被误判为「可清除」。必须把 `video_playback` 纳入消费类扫描。
2. **边界语义未显式落地**：`video`（原片）与 `video_frame`（帧图）目前仍走分析路径扫描，靠"路径不出现在 Analysis 里"侥幸判为可清除，语义错误且脆弱。

**修正规则（边界条件为准）**：

| upload_source | 是否小程序消费 | 判定 |
|---|---|---|
| `video_playback` / `skeleton` / `analysis_thumb` / `avatar` / `gear_image` | 是 | 被业务记录引用有效 → `in_use`；否则 → `unreferenced`（可清除·引用失效） |
| `video`（原片） / `video_frame`（抽帧帧图） | **否** | **恒为 `unreferenced`（可清除）**，不随任何业务引用变化 |

**实现要点**（`file_service.py` 两函数对称修改）：

- 新增常量 `CONSUMED_SOURCES`（消费类）与 `NON_CONSUMED_SOURCES = {"video","video_frame"}`。
- `src in NON_CONSUMED_SOURCES` → 直接返回 `("unreferenced", "原视频/抽帧帧图不被小程序直接消费，可清除")`，**不再做分析路径扫描**。
- 消费类：`video_playback` 加入兜底扫描集合（与 `skeleton`/`analysis_thumb`/头像/装备一致），按 Analysis/User/Gear 引用匹配；命中 → `in_use`，否则 `unreferenced`。
- 该分类对历史数据同样适用（消费类仍用路径匹配 Analysis 引用）；`original_video_info` 表落地后可作为更权威的「衍生↔分析」映射，但**非分类前置依赖**，避免表未建时分类失效。

**配套**：`app/schemas/admin_file.py`（`:10-12`）`unreferenced` 说明补充「或不被小程序直接消费（原视频整片/抽帧帧图），可清除」，使「可清除·引用失效」与边界标准一致。
