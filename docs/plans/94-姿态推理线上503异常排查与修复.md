# 94：姿态推理线上 503 异常排查与修复

## 一、背景与现象

**现象**：2026-08-17 09:02:08，魔搭创空间后台报 503，小程序上报埋点：

```
ERROR | pose:analyze:64 - 姿态推理异常
POST /api/pose/analyze: 503 姿态推理服务异常，请稍后重试
```

**环境**：
- 部署平台：魔搭创空间（阿里云内网，Docker 容器，2vCPU/16GB）
- Python：3.10.21（`python:3.10-slim`）
- mediapipe：构建期解析到 1.0.1（`uv pip install --no-cache .` 不读 uv.lock）
- numpy：2.2.6（容器内）
- 模型：`/app/models/pose_landmarker_lite.task`（5.7MB，sha256 已固化）

## 二、根因分析

### 2.1 异常路径定位

`server/app/routers/pose.py` 路由逻辑：

```python
def analyze(...):
    if not pose_service.is_available():          # line 41 → warning + 503 detail="模型缺失或 mediapipe 未安装"
        ...
    try:
        result = pose_service.analyze_frames(...) # line 49
    except ValueError as exc:
        raise HTTPException(400, ...)             # line 56
    except PoseUnavailableError as exc:
        log.error(f"姿态推理失败: {exc}", exc_info=True) # line 59 → 503 detail="姿态推理失败"
        ...
    except Exception as exc:
        log.error(f"姿态推理异常: {exc}", exc_info=True) # line 64 ← 命中这里
        raise HTTPException(503, "姿态推理服务异常，请稍后重试")
```

**关键线索：日志行号 `pose:analyze:64`**

| commit | 时间 | pose.py 行号 | ImageFormat 修复 | 模型随包 |
|--------|------|--------------|:---:|:---:|
| 21740b5 | 08-13 | **49** | ❌ (`mp_image_cls.ImageFormat`) | ❌ |
| d2802b4 | 08-14 | 62 | ✅ (`mp.ImageFormat`) | ✅ |
| **e743599** | **08-15** | **64** | ✅ | ✅ |
| HEAD (dev) | 08-17 | 64 | ✅ | ✅ |

线上日志行号 = **64** → 09:02 报错时线上已跑 **e743599 及之后** 的代码，**已包含 `mp.ImageFormat` 修复和模型随包逻辑**。

**推翻的假设**：之前推断的"旧代码 `mp_image_cls.ImageFormat` + mediapipe 1.0.x"假设**不成立**（否则会命中 line 49 而不是 line 64）。

### 2.2 已确认的根因（2026-08-18）

**最终异常消息**（日志修复后获取）：
```
姿态推理异常: libGL.so.1: cannot open shared object file: No such file or directory
```

**根因演变**：
1. **第一轮**：`libxcb.so.1` 缺失 → 已在 runtime 阶段添加
2. **第二轮**：`libGL.so.1` 缺失 → 说明 slim 镜像持续缺失图形库

**根本原因**：
- `python:3.10-slim`（Debian trixie slim）是精简镜像，不包含完整图形库
- mediapipe TFLite 运行时依赖多个图形库：`libxcb.so.1`、`libGL.so.1`、`libEGL.so.1` 等
- 手动添加依赖会导致"打地鼠"问题，每次部署都可能发现新缺失库
- 本地 Python 版本为 3.11.1，与容器 3.10 不一致

**解决方案**：改用 `python:3.11-slim` 精简镜像，在 runtime 阶段手动安装 mediapipe 所需的两个系统库：
- `libgl1`：提供 `libGL.so.1`（TFLite GPU 后端必需）
- `libglib2.0-0`：提供 `libgthread-2.0.so.0`（OpenCV 必需）

注意：`libxcb1` 是 `libgl1` 的依赖，会被自动安装，无需显式指定。

**改动**：两个 Dockerfile 统一更换基础镜像为 `python:3.11-slim`，在 runtime 阶段添加系统依赖安装。

**可排除的原因**：
- ❌ **模型缺失**：`is_available()` 返回 True（否则走 line 42 warning，不是 line 64）；d2802b4 起 Dockerfile 已 `COPY models/`。
- ❌ **mediapipe 未安装**：同上，`is_available()` 需要 mediapipe 可导入。
- ❌ **`mp.ImageFormat` 兼容**：e743599 已用正确写法；本地验证 1.0.0 下 `mp.ImageFormat.SRGB` 可用。

### 2.3 同类缺陷：日志丢失异常详情

**问题**：`LOG_FORMAT` 没有 `{extra}` 字段，`log.error("姿态推理异常", error=str(exc))` 的 `error=` extra 被丢弃，真实异常消息从未被记录。

**修复**：已改为 `log.error(f"姿态推理异常: {exc}", exc_info=True)`（2026-08-18 提交 `bd5f9d9`）。

同类缺陷在以下 3 处同时存在（均已修复）：

| 文件 | 行号 | 原写法 | 新写法 |
|------|------|--------|--------|
| `app/routers/pose.py` | 59 | `log.error("姿态推理失败", error=str(exc))` | `log.error(f"姿态推理失败: {exc}", exc_info=True)` |
| `app/routers/pose.py` | 64 | `log.error("姿态推理异常", error=str(exc))` | `log.error(f"姿态推理异常: {exc}", exc_info=True)` |
| `app/routers/video.py` | 90 | `log.error("视频处理失败", path=abs_path, error=str(exc))` | `log.error(f"视频处理失败: {exc}", path=abs_path, exc_info=True)` |

## 四、方案设计

### 4.1 日志修复（已完成 ✅）

**改动**：把 extra kwarg 改为嵌入消息体，同时加 `exc_info=True` 保留完整 traceback。

`server/app/routers/pose.py`：

```python
# line 59
- log.error("姿态推理失败", error=str(exc))
+ log.error(f"姿态推理失败: {exc}", exc_info=True)

# line 64
- log.error("姿态推理异常", error=str(exc))
+ log.error(f"姿态推理异常: {exc}", exc_info=True)
```

`server/app/routers/video.py`：

```python
# line 90
- log.error("视频处理失败", path=abs_path, error=str(exc))
+ log.error(f"视频处理失败: {exc}", path=abs_path, exc_info=True)
```

**效果**：
- 下次同类异常会看到完整报错（如 `OSError: libxcb.so.1: cannot open shared object file`）
- `exc_info=True` 会在控制台/文件日志里打印完整栈
- 不影响现有业务逻辑，纯观测层改动

### 4.2 mediapipe 版本锁定（已完成 ✅）

**现状**：

| 来源 | mediapipe 版本 |
|------|----------------|
| `pyproject.toml` | `>=0.10.14`（范围约束） |
| `uv.lock` | `==1.0.0`（2026-08-13 锁定） |
| 本地 venv | `==1.0.0`（通过 uv sync 解析） |
| Docker 构建 | `==1.0.1`（`uv pip install --no-cache .` 解析最新） |

**问题**：Docker 构建不读 uv.lock（`uv pip install` vs `uv sync`），会解析出最新版本。当前 1.0.1 与 1.0.0 API 基本一致，但未来升级可能引入 breaking change。

**方案**：

`server/pyproject.toml` 第 17 行：

```toml
- "mediapipe>=0.10.14",
+ "mediapipe==1.0.0",
```

然后执行：

```bash
cd server && uv lock
```

**备选**：也可改为 `mediapipe>=1.0.0,<1.1.0` 给小版本容错。但考虑到 uv.lock 已锁 1.0.0 且验证过，直接用 `==` 更严格。

### 4.3 更换基础镜像（已完成 ✅）

**根因演变**：
- 第一轮：`libxcb.so.1` 缺失 → 添加后
- 第二轮：`libGL.so.1` 缺失 → 说明 slim 镜像持续缺失图形库
- 第三轮：`libgthread-2.0.so.0` 缺失 → 确认 slim 镜像缺 OpenCV 依赖

**解决方案**：改用 `python:3.11-slim` 精简镜像，在 runtime 阶段手动安装必要系统库。

**改动**：两个 Dockerfile 统一更换基础镜像，runtime 阶段添加 apt-get 安装。

`server/modelscope/Dockerfile`：
```dockerfile
# 变更前
FROM python:3.11 AS builder
# ...
FROM python:3.11 AS runtime
# ...

# 变更后
FROM python:3.11-slim AS builder
# ...
FROM python:3.11-slim AS runtime
RUN apt-get update && apt-get install -y --no-install-recommends \
    libgl1 \
    libglib2.0-0 \
    && rm -rf /var/lib/apt/lists/*
```

`server/Dockerfile`：同上。

**说明**：
- `python:3.11-slim` 基础镜像约 125MB，最终构建镜像约 957MB（vs 原版 1.1GB）
- 手动安装 `libgl1` + `libglib2.0-0` 共约 15MB，精确控制依赖范围
- `libxcb1` 作为 `libgl1` 的依赖被自动安装，无需显式指定
- 已在本地 Docker 验证：`mediapipe==1.0.0` 导入、`PoseLandmarkerOptions` 创建、`cv2` 导入均正常
