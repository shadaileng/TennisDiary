# 94：姿态推理线上 503 异常排查与修复

## 一、背景与现象

**现象**：2026-08-17 09:02:08，魔搭创空间后台报 503，小程序上报埋点：

```
ERROR | pose:analyze:64 - 姿态推理异常
POST /api/pose/analyze: 503 姿态推理服务异常，请稍后重试
```

**环境**：
- 部署平台：魔搭创空间（阿里云内网，Docker 容器，2vCPU/16GB）
- Python：3.10.21（`python:3.10-slim`）
- mediapipe：构建期解析到 1.0.1（`uv pip install --no-cache .` 不读 uv.lock）
- numpy：2.2.6（容器内）
- 模型：`/app/models/pose_landmarker_lite.task`（5.7MB，sha256 已固化）

## 二、根因分析

### 2.1 异常路径定位

`server/app/routers/pose.py` 路由逻辑：

```python
def analyze(...):
    if not pose_service.is_available():          # line 41 → warning + 503 detail="模型缺失或 mediapipe 未安装"
        ...
    try:
        result = pose_service.analyze_frames(...) # line 49
    except ValueError as exc:
        raise HTTPException(400, ...)             # line 56
    except PoseUnavailableError as exc:
        log.error("姿态推理失败", error=str(exc)) # line 59 → 503 detail="姿态推理失败"
        ...
    except Exception as exc:
        log.error("姿态推理异常", error=str(exc)) # line 64 ← 命中这里
        raise HTTPException(503, "姿态推理服务异常，请稍后重试")
```

**关键线索：日志行号 `pose:analyze:64`**

| commit | 时间 | pose.py 行号 | ImageFormat 修复 | 模型随包 |
|--------|------|--------------|:---:|:---:|
| 21740b5 | 08-13 | **49** | ❌ (`mp_image_cls.ImageFormat`) | ❌ |
| d2802b4 | 08-14 | 62 | ✅ (`mp.ImageFormat`) | ✅ |
| **e743599** | **08-15** | **64** | ✅ | ✅ |
| HEAD (dev) | 08-17 | 64 | ✅ | ✅ |

线上日志行号 = **64** → 09:02 报错时线上已跑 **e743599 及之后** 的代码，**已包含 `mp.ImageFormat` 修复和模型随包逻辑**。

**推翻的假设**：之前推断的"旧代码 `mp_image_cls.ImageFormat` + mediapipe 1.0.x"假设**不成立**（否则会命中 line 49 而不是 line 64）。

### 2.2 可排除的原因

- ❌ **模型缺失**：`is_available()` 返回 True（否则走 line 42 warning，不是 line 64）；d2802b4 起 Dockerfile 已 `COPY models/`。
- ❌ **mediapipe 未安装**：同上，`is_available()` 需要 mediapipe 可导入。
- ❌ **`mp.ImageFormat` 兼容**：e743599 已用正确写法；本地验证 1.0.0 下 `mp.ImageFormat.SRGB` 可用。

### 2.3 仍可能的原因（generic exception in analyze_frames）

**已知事实**：
- 异常类型为 generic Exception（非 ValueError、非 PoseUnavailableError）
- 抛出点在 `analyze_frames` 内部某处
- **真实异常消息从未被记录**（见 §2.4 日志缺陷）

**候选原因**（按概率排序）：

1. **`_get_landmarker()` 的 `create_from_options` 抛 RuntimeError**
   - 容器内存/委托初始化（XNNPACK delegate）失败
   - 模型文件损坏或格式不匹配（sha256 已固化，概率低）
   - TensorFlow Lite 原生库加载失败（容器缺依赖）

2. **`landmarker.detect(image)` 抛 RuntimeError**
   - 输入 image bytes 解码异常（Pillow）
   - mediapipe 1.0.1 与 numpy 2.2.6 的底层交互问题
   - 内存压力（容器 16GB，偶发 OOM）

3. **`mp_image_from_bytes` 抛 OSError/UnidentifiedImageError**
   - base64 解码的 JPEG 帧数据损坏/截断
   - Pillow 无法识别的 JPEG 格式

4. **`encode_skeleton_video` / ffmpeg 子进程异常**
   - 仅当 `save_skeleton=true` 时触发
   - ffmpeg 不可用会 return False（不抛异常），排除

5. **numpy 2.2.6 与 mediapipe 1.0.1 兼容性**
   - 容器装的是 numpy 2.2.6（由 mediapipe 1.0.1 依赖解析决定）
   - 本地测试用 numpy 2.4.6 + mediapipe 1.0.0 正常
   - 无法在 plan mode 下复现，需实际部署验证

### 2.4 关键缺陷：异常消息从未被记录

`server/app/core/logging.py` 的 `LOG_FORMAT` 配置：

```python
LOG_FORMAT = (
    "<green>{time:YYYY-MM-DD HH:mm:ss.SSS}</green> | "
    "<level>{level: <8}</level> | "
    "<cyan>{module}</cyan>:<cyan>{function}</cyan>:<cyan>{line}</cyan> - "
    "<level>{message}</level>"
)
```

**没有 `{extra}` 字段**！`pose.py:64` 写的是：

```python
log.error("姿态推理异常", error=str(exc))
```

`error=` 是 loguru 的 **extra kwarg**，被 LOG_FORMAT 直接丢弃，真正的异常消息（如 `AttributeError: ...` / `RuntimeError: ...` / `OSError: ...`）**从未出现在任何日志中**。这导致本次排查花了大量时间做静态推断。

同类缺陷在以下 3 处同时存在：

| 文件 | 行号 | 原写法 |
|------|------|--------|
| `app/routers/pose.py` | 59 | `log.error("姿态推理失败", error=str(exc))` |
| `app/routers/pose.py` | 64 | `log.error("姿态推理异常", error=str(exc))` |
| `app/routers/video.py` | 90 | `log.error("视频处理失败", path=abs_path, error=str(exc))` |

## 三、目标

1. **修复日志**：让异常详情真正落盘（本次排查困难的直接根因）。
2. **锁定 mediapipe 版本**：消除本地/uv.lock/Docker 构建三方的版本漂移风险。
3. **确定并修复 503 根因**：通过修复后的日志复现，抓真实异常后精准修复。

## 四、方案设计

### 4.1 日志修复（高优先级，低风险）

**改动**：把 extra kwarg 改为嵌入消息体，同时加 `exc_info=True` 保留完整 traceback。

`server/app/routers/pose.py`：

```python
# line 59
- log.error("姿态推理失败", error=str(exc))
+ log.error(f"姿态推理失败: {exc}", exc_info=True)

# line 64
- log.error("姿态推理异常", error=str(exc))
+ log.error(f"姿态推理异常: {exc}", exc_info=True)
```

`server/app/routers/video.py`：

```python
# line 90
- log.error("视频处理失败", path=abs_path, error=str(exc))
+ log.error(f"视频处理失败: {exc}", path=abs_path, exc_info=True)
```

**效果**：
- 下次同类异常会看到完整报错（如 `AttributeError: ...` / `RuntimeError: ...`）
- `exc_info=True` 会在控制台/文件日志里打印完整栈（JSON 日志不记录 traceback，但 console 可见）
- 不影响现有业务逻辑，纯观测层改动

### 4.2 mediapipe 版本锁定（中优先级，防回归）

**现状**：

| 来源 | mediapipe 版本 |
|------|----------------|
| `pyproject.toml` | `>=0.10.14`（范围约束） |
| `uv.lock` | `==1.0.0`（2026-08-13 锁定） |
| 本地 venv | `==1.0.0`（通过 uv sync 解析） |
| Docker 构建 | `==1.0.1`（`uv pip install --no-cache .` 解析最新） |

**问题**：Docker 构建不读 uv.lock（`uv pip install` vs `uv sync`），会解析出最新版本。当前 1.0.1 与 1.0.0 API 基本一致，但未来升级可能引入 breaking change。

**方案**：

`server/pyproject.toml` 第 17 行：

```toml
- "mediapipe>=0.10.14",
+ "mediapipe==1.0.0",
```

然后执行：

```bash
cd server && uv lock
```

**备选**：也可改为 `mediapipe>=1.0.0,<1.1.0` 给小版本容错。但考虑到 uv.lock 已锁 1.0.0 且验证过，直接用 `==` 更严格。

### 4.3 503 根因复现（待日志修复后执行）

**步骤**：

1. 执行 §4.1 日志修复并部署
2. 在魔搭后台触发一次 `/api/pose/analyze` 请求（带真实视频帧 + save_skeleton=true）
3. 查看日志 `user.log`（或容器 stderr），定位完整异常消息和 traceback
4. 根据异常类型：
   - 若是 `RuntimeError` from `create_from_options` → 检查模型/委托/内存
   - 若是 `OSError` from Pillow → 检查帧数据完整性
   - 若是 numpy/mediapipe 兼容 → 调整版本或降级
   - 若是其他 → 精准修复

**本地复现辅助**（若线上复现困难）：

构造与容器同等环境的虚拟环境（Python 3.10 + mediapipe 1.0.1 + numpy 2.2.6），跑完整 `analyze_frames` 链路，尝试用真实视频帧数据触发同款异常。

## 七、风险与注意事项

| 风险 | 说明与对策 |
|------|-----------|
| `exc_info=True` 可能增加日志体积 | 仅在异常路径触发，正常请求不受影响 |
| JSON 日志格式不含 traceback | `JSON_FORMAT` 也没加 `{exception}`，但控制台/文件日志会打印，够用 |
| mediapipe 1.0.0 太旧 | 当前 1.0.1 与 1.0.0 API 一致；若需新版先本地验证 |
| 503 根因仍未确定 | 本方案 §4.1、4.2 为确定性改进；§4.3 留作后续跟踪项 |
